If you build web apps in Python, the interactive parts of a page often
mean a second project in JavaScript, with its own build and its own
copy of your data types. A typo in a template input often shows up only
when a visitor opens the page. And you often escape, sign and check
values by hand, or hope your template engine does it for you.

It can be safer, faster and smarter. We want to make Python web
development the best it can be, and Citry is our way there. Citry is a
typed frontend framework for Python, with server events and Vue.
Version 1.0.0, its first stable release, came out on 16 November 2026.

```console
python -m pip install -U "citry>=1.0.0,<2"
```

## What Citry is

A Citry component is a Python class. It owns its HTML template, its
browser behavior written in Vue, its CSS, its translations and the
Python methods that run when the visitor clicks or submits something
(its event handlers). You build an interactive page in one Python
codebase, without a separate frontend project. Citry works with
FastAPI, Django, Flask, Starlette, and any ASGI or WSGI app, on Python
3.11 to 3.15.

## Safer by default

Like most template engines, Citry escapes every ordinary value you
put in a template, so text from users cannot add tags to the page. Only
values marked as safe HTML, such as `Markup`, go in as they are. For
event handlers, Citry also signs the State it sends to the browser (the
values a handler needs between calls), so a user cannot change it
without Citry noticing, and it rejects calls to your handlers that come
from other sites.

You still check permissions in every handler and keep your framework's
CSRF check on. The [Security](/security/) page lists what Citry does
by default and what stays your job.

The maintainers also read 456 security advisories that other
frameworks and libraries published, among them Django, Next.js, Nuxt,
React and Vue, and checked Citry for each kind of bug that could apply
to it. A monthly job lists new advisories for review.
[How we check advisories](/security/#how-we-check) describes the
process.

## One codebase, fast pages

With one codebase, there is no second project to keep in step. When a
button needs to call Python, you write a method on the component and
bind it in the template. Citry sends the call to the server, and your
method decides how the page changes.

In Citry's own test, a page with 1,400 entries was usable in 257 ms on
its second load, after the server had served it once. Nuxt (Vue) was
faster, at 230 ms, and Next.js (React) took 324 ms. The maintainers
wrote the app in Citry and in eleven other frameworks, and the
[Benchmarks](/about/benchmarks/) page shows every number, the first
load, and how they were measured.

## Smarter tools

Citry's tools report mistakes before the app runs, and help you while
you write. A component declares its inputs as a typed class:

```citry
class Greeting(Component):
    class Kwargs:
        name: str
```

Suppose a page template misspells the input as
`<c-Greeting naem="Ada" />`. Point `citry check` at your app, here the
`citry` variable in the `shop` module, and it names the tag and the
inputs it accepts:

```console
$ citry --app shop:citry check
shop.Page.template: error: Parse error:  --> 3:3
  |
3 |   <c-Greeting naem="Ada" />
  |   ^-----------------------^
  |
  = Tag '<c-Greeting>' can only have the following attributes:
    'name', 'c-name', 'c-if', 'c-elif', 'c-else', 'c-for',
    'c-empty'. Found invalid attributes: naem.
```

The command imports your app module but starts no server, and it exits
with status 1 when it finds an error, so CI can fail the build.

In a separate test, the maintainers made the same 63 mistakes in the
app for each framework. With its editor and command-line checks, Citry
reported 56 of the 61 that apply to it before the app ran. Next.js with
TypeScript came next, with 45 of 57.

The free [VS Code extension](/ide/vscode/) adds completion, hover with
types, and go to definition from a template to the Python field, once
you install `citry-lsp` and point it at your app.

## What stable means

Code that uses what the docs describe keeps working in every 1.x
release. Pin `citry>=1.0.0,<2`.

There are two exceptions. Experimental features, such as component
previews and `EventsDispatcher`, may change in a minor release. A fix
that closes a security hole may also refuse input Citry used to
accept, and the changelog says so when it does.

Fixes go to the newest 1.x minor release, so keep upgrading within
1.x. After 2.0.0, the last 1.x minor release gets security fixes for
12 months. 0.x gets no more fixes.

The [UI library](/ui-library/), citry-ui, is not covered. It stays on
0.x, so pin one minor release, such as `"citry-ui>=0.6.0,<0.7"`.
[Versioning and support](/about/versioning/) has the exact rules and
the full list of [experimental features](/about/versioning/#experimental).

## Upgrade from the beta

The main steps:

1. Upgrade to the newest 0.9.x and follow its upgrade notes.
2. Install 1.0.0 with the command at the top.

0.9.0 made the last large set of breaking changes, so most apps need
no code changes. The one change most apps notice is about the State
token, the signed string that carries a component's State to the page.

- **What changed:** the token now expires after 24 hours, unless the
  component's `State` sets `_max_age`.
- **What visitors see:** after that, calls from the page fail until
  the visitor reloads it. In production Citry shows them nothing, so
  show your own message, as
  [Handle out-of-date pages](/reference/browser-apis/#out-of-date-pages)
  shows.
- **To change it:** set a longer `_max_age` in the component's `State`.

The language server `citry-lsp`, the VS Code extension and
`pygments-citry` are at 1.0.0 too. Upgrade `citry-lsp` and the
extension together. citry-ui 0.6.0 needs Citry 1.0.0 or later.

Step by step: [Upgrade to Citry 1.0.0](/guides/upgrading-to-1-0-0/).

[changelog](https://github.com/citry-dev/citry/blob/citry@1.0.0/CHANGELOG.md){: target="\_blank" rel="noopener"}.
