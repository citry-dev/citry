Rendering

The render pipeline, its output structs, Citry's trusted-HTML marker, and the Secret marker that keeps a value out of the data sent to the browser. citry.Markup is exactly markupsafe.Markup. Markup(value) trusts the complete value without sanitizing or validating anything. safe_eval runs an expression in the sandbox, unsafe marks a function that sandboxed expressions must not call, and SecurityError is what a blocked access raises. Four parts of this page are experimental and may change in a minor release: RenderFrame; the asset tags that deps_position="separate" returns (SerializedAssets, SerializedAssetEntry, the asset fields of SerializedRender, CitryRender.needs_browser_runtime(), combine_assets(), and OutsideSlotContentError); the API for embedding Citry tags in another template engine (CompiledBody, render_compiled_body and collect_compiled_body_fills); and page_nonce_from_headers(), which reads the page's CSP nonce from a request, with the PAGE_NONCE_HEADER name it reads.

CitryElement class

Intermediate representation of a component invocation.

Created by Component(). Holds the component class and the kwargs/slots that were passed. Rendering is deferred until .render() is called.

Attributes

  • comp_cls - The Component subclass to render.
  • kwargs - The keyword arguments passed to the component.
  • slots - The slot fills passed to the component. Filled from either channel: the reserved slots= kwarg when composing from Python (MyComp(title="x", slots={...})), or the collected <c-fill> tags / implicit default body when composed by a parent template. Values are raw inputs here (strings, functions, elements, Slots); they normalize to Slot instances when the component instance is created at render time.
  • component_tag_client_bindings - The final source-ordered bindings captured from a component tag, including native Vue props and event listeners and Citry server events. They are framework metadata, not Python kwargs.
  • element_morph_metadata - Private metadata materialized only by the dynamic ordinary-element built-in.

CitryRender class

The result of rendering a CitryElement (the render-phase output).

Experimental

The frame attribute, the frame= argument and the RenderFrame class they use are experimental. They may change in a minor release without a deprecation period. The rest of CitryRender is stable.

Attributes

  • parts - Ordered list of str or nested CitryRender fragments.
  • context - The CitryContext used to produce this render.
  • is_component_root bool - True for a nontransparent component's whole output. Transparent whole outputs and interior renders (a <c-if>/<c-for> block, a nested template, slot-fill content rendered in the enclosing scope) are False. Serialization uses this to tell a completed child-component subtree (which becomes its own marked frame) from content that joins into the surrounding frame; the component on the context cannot tell these apart, because slot-fill content carries the context of the component that wrote it, not the one it renders inside.

needs_browser_runtime function 

needs_browser_runtime() -> bool

Whether this render has browser behavior that needs Citry's browser runtime.

It returns True when a component in this render uses js_data(), a Vue binding such as @click or :title, component JavaScript, or server events. Then serialize() with the "document" or "fragment" strategy puts the HTML in an element that Vue mounts on, and adds the runtime. It returns False when the serialized HTML works without Citry's JavaScript.

The answer depends only on what was rendered, not on the serialize() arguments: with security_javascript="omit" or "forbid", serialize still leaves out the runtime or refuses the render.

Code that combines Citry renders with HTML from another template engine can use it to pick which child renders become their own Vue apps. A child component's render may be serialized on its own before its parent is serialized. It becomes a separate Vue app with its own assets, and the parent's render does not change, so the parent can still be serialized afterwards. This works only when the child holds no slot content that a component outside it wrote, such as text the parent passed between the child's tags; serializing such a child on its own raises OutsideSlotContentError, a TypeError.

Experimental

This method may change in a minor release without a deprecation period.

Example

rendered = Page().render()
apps = [
    part.serialize_result(deps_position="separate")
    for part in rendered.parts
    if isinstance(part, CitryRender)
    and part.is_component_root
    and part.needs_browser_runtime()
]

Returns

bool: Whether this render needs Citry's browser runtime.

has_server_events function 

has_server_events() -> bool

Whether this render has a component with server events.

It returns True when a component in this render declares class Events. Then serialize() gives the browser what it needs to call that component's event handlers. It returns False when no event call can come from this render. It answers from what Citry recorded while rendering, so you can call it before serialize(), and it does not change the render.

To decide whether a page needs the CSRF cookie, use needs_csrf_token(), which also covers the other browser requests that send the token.

Like needs_browser_runtime(), the answer depends only on what was rendered, not on the serialize() arguments. It can return True even when security_javascript="omit" or "forbid" makes serialize() leave the event handlers out or refuse the render. A child component's render answers for that child alone, which is what serializing it on its own gives.

Experimental

This method may change in a minor release without a deprecation period.

Example

rendered = Page().render()
if rendered.has_server_events():
    ...  # the page can call server event handlers

needs_csrf_token function 

needs_csrf_token() -> bool

Whether the browser may send Citry's CSRF token from this render.

It returns True when serializing this render lets the browser send a request that carries the page's CSRF token, which the host's CSRF check, such as Django's CsrfViewMiddleware, then verifies. Citry's browser code sends the token on these requests:

  • an Events call to a component's event handlers, a POST to the events route, when has_server_events() returns True;
  • a request for translated messages, a POST to ext/i18n/messages, which the browser sends when it needs a locale the page did not include, such as on $i18n.switchLocale(). Citry sends it only when its routes are mounted, from a render that has a <c-i18n client> provider or that is rendered into one.

It returns False when neither can come from this render.

Host integrations such as citry-django use it to set the CSRF cookie only on pages that need it, because the cookie keeps shared caches from storing the page. It answers from what Citry recorded while rendering, so you can call it before serialize(), and it does not change the render.

It does not cover requests that your own code sends. A form you write that posts to an event URL needs your framework's CSRF field, and a browser plugin from a third-party extension that adds csrfHeaders() to its own requests needs the cookie too.

Like has_server_events(), the answer depends only on what was rendered, not on the serialize() arguments, and a child component's render answers for that child alone. It may return True when serialization writes no such request, which only costs a cookie the page did not need.

Experimental

This method may change in a minor release without a deprecation period.

Example

rendered = Page().render()
if rendered.needs_csrf_token():
    get_token(request)  # Django sets the CSRF cookie
html = rendered.serialize()

serialize function 

serialize(deps_strategy: DepsStrategy = 'document', deps_position: DepsPosition = 'smart', csp_nonce: str | None = None, security_csp: SecurityCspMode | None = None, security_javascript: SecurityJavascriptMode | None = None, security_script_integrity: SecurityScriptIntegrityMode | None = None, ssr: bool | None = None) -> str

Turn this render into a final HTML string.

In static output, each component's root element gets a data-cid-<id> attribute. When a rendered component needs Vue in the browser, Citry keeps the surrounding page markup, puts the rendered content (the page body, for a full document) in one element where Vue mounts, and adds the data and scripts Vue needs to mount it. Citry places the collected JS/CSS according to deps_strategy and deps_position.

With security_csp="warn", Citry reports content that would break under a Content Security Policy but leaves the output unchanged. With "strict", it raises instead of warning, and it requires csp_nonce when Citry emits an executable script or a <style> element. With security_javascript="warn", it reports which components need JavaScript; "omit" drops Citry's scripts but keeps the HTML and CSS; "forbid" raises when a rendered component needs browser behavior.

Parameters

  • deps_strategy DepsStrategy -

    How to handle the collected JS/CSS.

    • "document" (default): emit the tags, plus Citry's Vue browser runtime and the data it needs to mount the page when a component needs per-instance browser behavior, such as js_data() values on its Vue instance or $component callbacks.
    • "simple": the tags only, no JavaScript runtime. For static pages and emails; per-instance JS does not run (CSS variables still work, they are pure CSS).
    • "fragment": HTML meant to be inserted into an already-loaded page (an HTMX swap, fetch + innerHTML, ...). A fragment without browser behavior carries its tags directly. An interactive fragment carries a script that loads Citry's browser runtime if the page does not have it yet, plus JSON that tells the runtime which assets to load before it mounts the fragment. A fragment that carries JS, CSS, or browser behavior requires a mounted web integration.
    • "ignore": no tags inserted.
  • deps_position DepsPosition -

    Where the tags go (document/simple only; "separate" also accepts ignore).

    • "smart" (default): into the <c-js>/<c-css> placeholders when present, else CSS before the first </head> and JS before the last </body>, else CSS is prepended and JS appended.
    • "prepend" / "append": all tags before/after the whole output.
    • "separate" (Experimental): no tags in the HTML. serialize_result() returns them in the asset fields of SerializedRender, so a page that combines several renders can write each shared tag once. Vue adopts the server HTML as it does with "smart". serialize() returns only the HTML and drops the tags, so use serialize_result().
  • csp_nonce str | None - Raw request nonce to add to structured scripts and inline styles. The host owns nonce generation and the matching Content-Security-Policy response header.
  • security_csp SecurityCspMode | None - Override this render's engine-level CSP policy.
  • security_javascript SecurityJavascriptMode | None - Override this render's engine-level JavaScript delivery policy.
  • security_script_integrity SecurityScriptIntegrityMode | None - Override security_script_integrity for this render.
  • ssr bool | None - Override the engine's initial Vue HTML hydration setting. None uses the ssr setting.

Raises

  • RuntimeError - If a child component was left unrendered, which can only happen when this render did not come from render(); if the same render is placed more than once in the output; if deps_strategy="fragment" needs a mounted web integration and none is mounted; or if, with deps_position="separate", an extension's on_serialize hook changed one of the asset tags.
  • ValueError - If an argument is invalid, such as deps_position="separate" with a deps_strategy other than "document", "simple" or "ignore"; if security_csp="strict" rejects the output or the output needs csp_nonce and none was given; or if security_javascript="forbid" finds a component that needs browser behavior; or if a component uses Events and no web integration is mounted.
  • TypeError - If ssr is not a bool or None.
  • OutsideSlotContentError - If this render is a child component's render that needs Vue and holds slot content that a component outside it wrote. It subclasses TypeError.

serialize_result function 

serialize_result(deps_strategy: DepsStrategy = 'document', deps_position: DepsPosition = 'smart', csp_nonce: str | None = None, security_csp: SecurityCspMode | None = None, security_javascript: SecurityJavascriptMode | None = None, security_script_integrity: SecurityScriptIntegrityMode | None = None, ssr: bool | None = None) -> SerializedRender

Return final HTML together with security metadata for those exact bytes.

Arguments and validation match serialize(); this method also returns the security metadata a host needs, while serialize() returns only result.html.

With deps_position="separate", the result's html holds no asset tags, and its runtime_assets, app_assets and component_assets hold them instead. Each group's css_entries and js_entries say which components declared each tag. See Combine several renders and Find a tag's components.

Example

result = Widget().render().serialize_result(
    deps_position="separate",
)
groups = [
    result.runtime_assets,
    result.component_assets,
    result.app_assets,
]
head = "".join(tag for g in groups for tag in g.css)
end_of_body = "".join(tag for g in groups for tag in g.js)

SerializedRender class

Final HTML plus host-facing security metadata for those exact bytes.

The asset fields are empty unless the render was serialized with deps_position="separate". Then html holds none of the tags Citry places (tags that another extension's on_serialize hook adds stay in it), and the tags are split into three groups so a page that combines several renders can write each shared tag once. security covers the HTML and the tags in these groups.

Attributes

  • html str - The serialized HTML.
  • security SerializedSecurity - Security metadata, such as the hashes a Content Security Policy needs, for html and the asset groups below.
  • runtime_assets SerializedAssets - Experimental. Citry's own code that every Vue app on a page shares: the browser runtime, the scripts that extensions add to it, preload hints, and, when no web integration is mounted, the compiled component code. Write the first of each set of identical tags and skip the rest.
  • app_assets SerializedAssets - Experimental. The tags of this render's one Vue app: its stylesheets, its configuration data and its start script. Write every one of them, or pass this group from every render to combine_assets(), which writes one stylesheet tag for the apps that share it.
  • component_assets SerializedAssets - Experimental. The other tags: component CSS and JavaScript when no component needs Vue, dependency files, and tags added by on_dependencies hooks. Write the first of each set of identical tags and skip the rest.

SerializedAssets class

One group of asset tags that deps_position="separate" returns instead of inserting.

Each item is one complete tag, written exactly as Citry would have inserted it, with the same nonce, integrity and other attributes.

SerializedAssetEntry class

One asset tag, with the components that declared it.

Citry fills these fields from what it recorded while it rendered each component. So code that bundles or caches tags can decide what to do with a tag without reading its attributes.

Experimental

SerializedAssetEntry and the css_entries and js_entries fields of SerializedAssets are experimental. They may change in a minor release without a deprecation period.

Attributes

  • tag str - The complete tag, the same string as in css or js.
  • class_ids tuple[str, ...] - The class_id of each component that declared this tag, in the order the render first used them. There is more than one when components declare the same file or the same CSS text. It is empty for Citry's own tags, such as the browser runtime, preload hints and a Vue app's data and start script, and usually for a Vue app's stylesheets, whose components the app tracks itself. A tag that an on_dependencies hook added or rebuilt names only its own origin_class_id, or nothing when the hook set none.
  • instance bool - True when the tag may hold data from one render, so it may differ between renders: a stylesheet with one instance's css_data() values, every tag in app_assets, and any tag that Citry cannot show is the same on every render, such as one an on_dependencies hook added or rebuilt. Do not put such a tag into a file that other pages share. False only for the tags in runtime_assets and for a component's own or Dependencies tags, which are the same wherever the component is used.

combine_assets function 

combine_assets(groups: Iterable[SerializedAssets]) -> SerializedAssets

Combine the same group of asset tags from several renders, writing each shared tag once.

Pass one group from every render, such as each result's app_assets, and write the returned tags in place of theirs. Call it once per group, so the tags of one group never move into another.

  • Identical tags are kept once, where they first appear.
  • Stylesheet tags of several Vue apps that serve the same file become one tag that names every one of those apps, so the browser runtime lets each app use it. Each app's configuration data and start script stay as they are, because they differ per app.
  • Every other tag is kept as it is, with its nonce and integrity.
  • When every group that has css tags also has css_entries, the result has them too, and the same for js. A merged tag's entry lists the components of every tag it replaced, and has instance=True when any of them does. A group that has tags but no entries leaves the result without entries for that kind.

The tags come in the order of the groups you pass, and within a group in the order the render gave them. A tag several renders share stays where it first appears, so a later render's stylesheets can end up in a different order than that render alone would write them.

Experimental

combine_assets is experimental. It may change in a minor release without a deprecation period.

Example

results = [
    Widget().render().serialize_result(
        deps_position="separate",
    ),
    Chart().render().serialize_result(
        deps_position="separate",
    ),
]
apps = combine_assets(
    result.app_assets for result in results
)

Parameters

  • groups Iterable[SerializedAssets] - The same group, such as app_assets, from each SerializedRender that serialize_result(deps_position="separate") returned.

OutsideSlotContentError class

Bases: TypeError

Raised when a child render that holds slot content from outside it is serialized on its own as a Vue app.

A child component's render may be serialized on its own before its parent, and it then becomes its own Vue app. That fails when the child holds slot content that a component outside it wrote, such as text the parent passed between the child's tags, because nothing in the new app owns that content. Serialize the component that wrote the slot content instead.

It subclasses TypeError, so except TypeError also catches it.

Experimental

OutsideSlotContentError is experimental. It may change in a minor release without a deprecation period.

page_nonce_from_headers function 

page_nonce_from_headers(headers: Mapping[str, str]) -> str | None

Return the CSP nonce a request says its page has, or None.

Under a nonce-based Content Security Policy, the browser starts a Vue fragment only when it carries the nonce of the page it lands in. When page code loads a fragment with its own request (htmx, fetch()), it sends that nonce in the X-Citry-Page-Nonce header, from Citry.pageNonce() in the browser. Pass the result as csp_nonce when you serialize the fragment, so it carries the nonce of the tab that asked for it.

The answer depends on the header, so list X-Citry-Page-Nonce in its Vary header, and when the result is not None also send Cache-Control: no-store. A shared cache could otherwise give one visitor's nonce to another.

Experimental

The header name and this function may change in a 1.x minor release without a deprecation period.

Example

nonce = page_nonce_from_headers(request.headers)
html = card.render().serialize(
    deps_strategy="fragment",
    csp_nonce=nonce,
)

Parameters

  • headers Mapping[str, str] - The request headers, such as Django's request.headers. Header names match without regard to case.

CitryContext class

Render-scoped state for a single component render.

Attributes

  • variables - The per-component template variables (the template_data output). Read by nodes when evaluating expressions. Values are ordinary Python objects; the private mapping stores any Const promise separately by variable name.
  • component - The Component instance currently rendering. Gives a node access to the component tree (its citry registry for resolving child component names, and its parent/root linkage). The current component is stored on the context, so each component render gets its own CitryContext.
  • extra - Tree-wide scratch space for extensions (for example the collected JS/CSS dependency records). Citry does not copy these entries itself: when a child render is placed into its parent, Citry calls the on_render_context_merge hook, and each extension copies its own entries from the child's extra into the parent's. By convention, each extension stores its data under a top-level key named after itself (extra["dependencies"]). Citry uses some other top-level keys too, so choose a distinctive name.
  • provides - The provide/inject entries active at this point of the render. Entries may hold a direct caller value, a frozen keyword- field payload, or a private blocked marker. Read-only by convention; Component.provide and Component.unprovide build a new mapping rather than mutating this one.

Placeholder class

A spot in the output whose final text is supplied at serialize time.

Rendered output is normally text and nested renders, fixed once rendered. A Placeholder marks a position whose content is only known when the whole page is serialized: the <c-js> / <c-css> built-ins render one each, and the dependencies extension fills them with the collected script/style tags via the on_serialize hook.

Attributes

  • key - What belongs at this spot (e.g. "deps:js"). The serializer reports each occurrence to the on_serialize hook under this key plus a counter and a private per-serialization identity. An extension that knows the key supplies the text; an occurrence no extension fills serializes to nothing. The private identity keeps cleanup from matching an authored <template c-render-id> with the same key and counter.

Secret class

Bases: Generic

Wrap a server-only value, such as an API token, so Citry never sends it to the browser.

Citry sends everything Component.js_data() returns to the browser, where anyone can read it in the page source. Wrap a value in Secret to have Citry refuse to send it.

Rendering a component raises a TypeError that names the component and the key, before any HTML is sent, when a Secret is anywhere in the dicts and lists js_data() returns. A Secret in a Component.css_data() value or a State field raises ValueError, whether or not the component has CSS. citry --app ... check also warns when it can see the Secret: a module-level Secret that js_data() puts in its result, such as {"token": API_TOKEN}, or reads from an attribute stored on a module or a plain class, such as config.API_TOKEN (not through a property or a lazy settings object), or a JsData field annotated Secret[str].

A Secret that js_data() returns in another place, such as inside a dataclass instance nested in the result, as a dict key, or in a set, is refused too, but by the TypeError for any value JSON cannot carry, which does not name the key.

On the server a Secret keeps its value hidden. Call get_secret_value() where you need the value, for example to call an API in an event handler. Everywhere Python turns it into text it shows *** instead: str(), repr(), f-strings, logs, and {{ token }} in a template. So passing a Secret to a template or to a child component's Kwargs is allowed and never prints the value.

A child that uses the render cache cannot take a Secret this way. Without Cache.vary(), its cache key is built from all of its kwargs, and a Secret cannot be part of a key, so rendering raises CacheKeyError. Return values that are not secret, such as a user id, from that child's Cache.vary(), or leave the child uncached.

Annotate a Kwargs or TemplateData field as Secret[str] (or Secret[bytes], and so on) so a plain value passed there is rejected. The type in brackets is only for type checkers: check_input_types tests that the value is a Secret, not what it holds. When Kwargs is a Pydantic model, Pydantic's own error for a plain value prints that value; add model_config = ConfigDict(hide_input_in_errors=True) to the model to keep it out of the message.

A Secret never equals a plain value: API_TOKEN == sent is always False. To check a value a user sent, use hmac.compare_digest, which takes the same time however much of the input matches:

token = API_TOKEN.get_secret_value().encode()
# An unset variable gives an empty token, which an empty
# input would match, so refuse it first.
if not token:
    raise RuntimeError("API_TOKEN is not set")
matches = hmac.compare_digest(token, sent.encode())

Compare bytes, as here: compare_digest raises TypeError for text that is not ASCII. Two secrets are equal when their values are equal. When both values are str, or both are bytes, they are compared with hmac.compare_digest. Any other values are compared with ==.

A Secret cannot be changed after it is created. It can be a dict key when its value is hashable, and equal secrets hash alike. bool() is the truth value of the wrapped value, so if token: tells whether a token is set. Copying or pickling a Secret keeps the value, so a pickle still holds it in readable form.

Citry detects only values you wrap. A secret kept in a plain str is sent like any other string.

Example

Read a token on the server, and send the browser only the result:

import os

from citry import Component, Secret

API_TOKEN = Secret(os.environ["API_TOKEN"])


class Board(Component):
    def template_data(self, kwargs, slots):
        token = API_TOKEN.get_secret_value()
        return {"rows": load_rows(token)}

    def js_data(self, kwargs, slots):
        # Returning API_TOKEN here raises TypeError.
        return {"apiBase": "/api"}

    template = '''
      <ul>
        <c-for each="row in rows">
          <li>{{ row }}</li>
        </c-for>
      </ul>
    '''

Parameters

  • value T - The value to keep on the server. Any type works.

Raises

  • TypeError - When value is already a Secret. Pass that Secret on as it is instead of wrapping it again.

safe_eval function 

safe_eval(source: str, validate_variable: Callable[[str], bool] | None = None, validate_attribute: Callable[[Any, str], bool] | None = None, validate_subscript: Callable[[Any, Any], bool] | None = None, validate_callable: Callable[[Callable], bool] | None = None, validate_assign: Callable[[str, Any], bool] | None = None) -> Callable[[Mapping[str, Any]], Any]

Compile a Python expression into a function that runs it inside the sandbox Citry uses for template expressions. Call the result with a mapping of the names the expression may read. A blocked call, attribute, or name raises SecurityError when the expression runs. Pass only expression text that you or the template author wrote, never text from a request or from stored user data, because the sandbox does not block everything. See Sandbox template code for what the sandbox blocks and what it misses.
