Diagnostic reference

Every error and warning Citry reports has a code, such as citry.template.unknown-variable. The editor shows it next to the message, and citry check prints it with each finding. Find the code below to see what went wrong and how to fix it.

The code always names the same mistake in every tool: the editor, citry check, citry format, and the template parser. The message can add details, such as the name you misspelled.

Some rules can be made stricter or turned off. Those entries say "Your application can change this severity". For the template lint rules, see Template linting.

Codes that start with citry.python. or citry.typescript. come from the Python and TypeScript type checkers. They are listed at the end of this page.

citry.parse.syntax

Invalid template syntax. The template has a syntax mistake, such as an unclosed element or an unfinished expression. Citry cannot read the template, so it does not render.

Example: Unclosed element

<section>
  <p>Hello</p>

Fix: Correct the template at the reported position. The message says what the parser expected there.

When this appears: The parser finds malformed markup, an incomplete expression, or another syntax error. Only the first syntax error in a template is reported.

Default severity: error. Reported by: template parser APIs, citry format, citry check, citry-lsp.

citry.parse.value

Invalid template value. Citry was given a value it cannot parse as a template. This is usually not a mistake in your template text.

Fix: If an extension adds its own template syntax, update it or report the message to its authors. Otherwise, report the message as a Citry bug.

When this appears: A parser API receives a value it cannot turn into template source, for example when an extension that adds its own template syntax reports positions that do not fit the template.

Default severity: error. Reported by: template parser APIs, citry format, citry check, citry-lsp.

citry.parse.too-deep

Template nested too deeply. The template nests tags deeper than Citry allows, so it does not render.

Example: Tags of any kind past the total limit

<div>
  <div>
    <!-- ... 510 more nested <div> tags ... -->
    <p>Too deep</p>
  </div>
</div>

Example: Logic tags past the logic limit

<c-if cond="a">
  <c-for each="item in items">
    <!-- ... 254 more nested logic tags ... -->
    <c-if cond="b">Too deep</c-if>
  </c-for>
</c-if>

Fix: Move the inner part into its own component's template, which starts counting from zero. Markup passed to a component between its tags still counts toward the template that writes it.

When this appears: A tag would sit more than 512 levels deep, or more than 256 Citry logic levels deep: every c- tag except <c-raw>, and each c-if=, c-elif=, c-else, c-for= or c-empty attribute. A template inside an attribute counts from the depth of the tag that holds it.

Default severity: error. Reported by: template parser APIs, citry format, citry check, citry-lsp.

citry.parse.configuration

Template parser setup failed. Citry could not set up the template parser for your application, so it cannot check this template.

Fix: Read the message for the rule that failed, and fix the application or extension that defines it.

When this appears: The tag rules that your application or its extensions add to the parser cannot be built or applied.

Default severity: error. Reported by: citry check, citry-lsp.

citry.template.unknown-variable

Unknown template variable. A template reads a variable that nothing provides, often because of a typo. Rendering then fails with a KeyError.

Messages:

  • Closed template data:

    Template variable '{name}' is not available in this template.

  • Template data allows extra names:

    Template variable '{name}' is not declared. It may be supplied dynamically.

  • Template data could not be inspected:

    Template variable '{name}' is not declared. Citry could not determine whether it is supplied dynamically.

Example: Unknown name in an interpolation

<p>{{ missing_name }}</p>

Example: Unknown name in a dynamic attribute

<div c-title="missing_name"></div>

Fix: Correct the name, or add it to the data that template_data() returns. If template_data() builds its result in a way Citry cannot read, such as by calling a helper function, list every key it returns in Lint.template_data_keys. If another integration provides the name, declare it in template_variables, or change rule_unknown_template_variable.

When this appears: A name in {{ ... }} or in a c-* attribute is not in the component's template data, a c-for or c-fill binding around it, template_globals, or the declared template_variables. In a template that several components share, every one of them must provide the name.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.undeclared-template-data-key

Key missing from template_data_keys. A component's template_data() returns a key that its Lint.template_data_keys does not list, so the list no longer names every key the method returns.

Message:

template_data() returns '{name}', but Lint.template_data_keys does not list it. Add '{name}' to the list so it names every key the method returns.

Example: A key the list leaves out

class Card(Component):
    class Lint:
        template_data_keys = ("title",)

    def template_data(self, kwargs, slots):
        data = build_card(kwargs)
        data["badge"] = "new"
        return data

Fix: Add the key to Lint.template_data_keys, or stop returning it.

When this appears: A component declares Lint.template_data_keys, and its template_data() writes a key as a literal, such as {"title": ...} or data["title"] = ..., that the list leaves out.

Default severity: warning. Reported by: citry check.

citry.template.unknown-component

Unknown component. A component tag names a component that your application does not register, often because of a typo. The template fails to render.

Message:

Component <{tag}> is not registered.

Example: Unregistered component tag

<c-missing-card />

Fix: Correct the tag name, or register the component with the application that Citry loaded.

When this appears: A <c-*> tag names no component in the selected application or library, counting built-in names and aliases.

Default severity: error. Reported by: citry check, citry-lsp.

citry.template.marker-name-invalid

Invalid <c-mark> tag. A <c-mark> tag, which marks part of a component that an event handler can replace, has no usable name, an extra attribute, or content it does not accept.

Messages:

  • dynamic:

    Marker name must be a static literal.

  • invalid:

    Marker name must match [A-Za-z][A-Za-z0-9_-]*.

  • missing:

    Marker requires a literal name attribute.

  • extra:

    Marker accepts only its name attribute.

  • named_fill:

    Marker accepts only its default slot.

Fix: Give the marker one literal name that starts with a letter and contains only letters, digits, _ or -. Remove other attributes and named fills.

When this appears: A <c-mark> tag has no name attribute, a dynamic or invalid name, any other attribute, or a named fill.

Default severity: error. Reported by: citry check, citry-lsp.

citry.template.alpine-attribute

Alpine attribute on an HTML element. An HTML element still has an Alpine x-* attribute, such as x-data or x-on:click. Citry uses Vue, so nothing reads it and it does nothing.

Message:

'{name}' is an Alpine attribute. Citry uses Vue, so nothing reads it. Replace it with its Vue form, or set rule_alpine_attribute to 'ignore' if a library on the page reads '{name}'.

Example: Alpine state on an element

<div x-data="{ open: false }">
  <button x-on:click="open = !open">Menu</button>
</div>

Fix: Move the state into js_data() or $component, and write the listener in its Vue form, such as @click. If another library on the page reads x-* attributes, set rule_alpine_attribute to "ignore".

When this appears: An Alpine directive name, such as x-data, x-on:click, or x-intersect, sits on an HTML element or <c-element>, including inside nested templates. Other x-* names, such as x-webkit-airplay, are ordinary HTML. Component tags are not checked, because an x-* attribute there is a Python keyword argument. x-cloak is reported as citry.template.alpine-cloak.

Default severity: warning. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.alpine-cloak

x-cloak hides an element for good. An HTML element still has x-cloak. Nothing removes it, so a [x-cloak] CSS rule hides the element for good.

Message:

Nothing in Citry removes 'x-cloak', so a '[x-cloak]' CSS rule keeps this element hidden. Delete 'x-cloak' and its '[x-cloak]' rule; the server-rendered HTML already shows the content.

Example: Leftover x-cloak

<div x-cloak>{{ message }}</div>

Fix: Delete x-cloak and its [x-cloak] CSS rule. The HTML from the server already shows the content.

When this appears: x-cloak, in any letter case, sits on an HTML element or <c-element>, including inside nested templates. Component tags are not checked.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.invalid-attribute-value

HTML attribute value the browser does not accept. An HTML attribute that accepts only certain keywords, such as draggable or type, has another value, or a boolean attribute such as disabled has a value other than empty or its own name, which still turns it on. The browser raises no error either way.

Messages:

  • default:

    '{value}' is not a valid value for '{attribute}' on <{element}>. Valid values: {allowed}.

  • suggestion:

    '{value}' is not a valid value for '{attribute}' on <{element}>. Did you mean '{suggestion}'? Valid values: {allowed}.

  • empty:

    '{attribute}' on <{element}> needs a value. Valid values: {allowed}.

  • target:

    '{value}' is not a valid value for '{attribute}' on <{element}>. A name that starts with '_' must be one of: {allowed}.

  • frame-name:

    '{value}' is not a valid value for '{attribute}' on <{element}>. A frame name cannot start with '_'.

  • pragma:

    '{value}' is not a pragma browsers act on in '{attribute}' on <{element}>. If it is an HTTP header, send it in the HTTP response instead. Valid values: {allowed}.

  • boolean:

    '{attribute}' on <{element}> is on whenever it is present, so '{value}' still turns it on. Write it with no value to turn it on, and leave it out to turn it off.

  • boolean-binding:

    '{attribute}' on <{element}> is on whenever it is present, so the string '{value}' still turns it on. Bind a JavaScript boolean instead, such as :{attribute}="false".

Example: A misspelled keyword

<div draggable="treu">Drag me</div>

Example: An input type the browser does not know

<input type="datetime" name="start">

Example: A boolean attribute set to false

<button disabled="false">Search</button>

Fix: Use one of the valid values the message lists. For a boolean attribute, write it with no value, leave it out, or bind a JavaScript boolean such as :disabled="saving". If a script on the page reads its own values from the attribute, set rule_invalid_attribute_value to "ignore" for that component.

When this appears: The value is not one of the keywords the HTML Standard lists for that attribute on that element. A boolean attribute, such as disabled or required, is on whenever it is present, so any value other than the empty string or the attribute's own name is reported, including "false" and "true". Letter case does not matter, except for list markers in type on <ol> and <li>. A Vue binding whose value is one JavaScript string, such as :dir="'rtl'", is checked too. Other bound values, component tags, <c-element>, custom elements, elements inside <svg> or <math>, and attributes that take a list of words, such as rel, are not checked. citry check --static and an editor that has not loaded your application report it as a warning unless the component's own Lint class sets the rule as a plain string, because they cannot read your LintSettings.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.misspelled-directive

Misspelled Citry directive. A c-* attribute on an HTML element looks like a Citry directive, such as c-iff for c-if, but is not one, so Citry renders it as an ordinary attribute and the directive never runs. Or a v-* attribute looks like a Vue directive, such as v-iff for v-if, so Vue looks for a custom directive of that name and the page fails.

Messages:

  • default:

    '{name}' is not a Citry directive, so it renders an HTML attribute named '{attribute}'. Did you mean '{suggestion}'?

  • vue:

    '{name}' is not a Citry directive, so it renders an HTML attribute named '{attribute}'. For Vue's directive, write '{suggestion}'.

  • vue-directive:

    '{name}' is not a Vue directive, so Vue looks for a custom directive of that name and the page fails in the browser. Did you mean '{suggestion}'?

Example: A typo in c-if

<div c-iff="show">Details</div>

Example: A directive name from Vue

<input c-model="query">

Example: A typo in v-if

<p v-iff="open">Details</p>

Fix: Use the directive the message names. For a custom directive, register it in the directives option of $component({...}). If the attribute really is meant for the browser, pass it through c-bind, such as c-bind="{'show': value}". For a directive a plugin registers, set rule_misspelled_directive to "ignore" for that component.

When this appears: The part after c- is not an HTML attribute that the element accepts, and it looks like a directive: if, elif, else, for, empty, or bind with two neighboring letters swapped, one letter typed twice, or one letter left out, such as c-fro, c-iff, or c-ele; one of those in other letter case, such as c-If; a spelled-out c-elif, such as c-else-if; c-show for c-if or c-model for v-model; or c-key or c-ignore without the #. A different letter, or an extra letter that is not a double, is not a typo, because it usually makes an ordinary word such as c-kind or c-form; neither are c-or, c-bid, c-bin, or a one-letter name. On a custom element, which can define its own attributes, the c-show, c-model, c-key, and c-ignore names are not reported. Only HTML elements, custom elements, and <c-element> are checked, not component tags or elements inside <svg> or <math>. A v-* name is reported on any element outside <svg>, <math>, and v-pre content, component tags included, when it is not a Vue directive and it is a typing slip (two neighboring letters swapped, one letter typed twice, or one letter left out) away from one, such as v-iff, v-shwo, or v-IFF, or is a spelled-out v-else-if, such as v-elif or v-elseif. A custom directive whose name is one slip from a Vue directive is not reported when every component that renders the template registers it in the directives option of $component({...}), under the name as written, its camelCase form, or that form with a capital first letter, such as directives: { iff: {...} } for v-iff or { myDir: {...} } for v-my-dir. Only citry check without --static and an editor that has loaded your application skip it. It is still reported when Citry cannot read that option, and for a directive that a plugin registers with Citry.vue.use(plugin), which no check can see. citry check --static and an editor that has not loaded your application report it too, with the severity the component's own Lint class sets as a plain string.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.misspelled-attribute

Misspelled HTML attribute. An attribute on an HTML element looks like a typo of an attribute that element accepts, such as titel for title. The browser keeps it as an unknown attribute and ignores it, with no error.

Message:

'{name}' is not an attribute of <{element}>, so the browser ignores it. Did you mean '{suggestion}'?

Example: A typo in title

<div titel="Board">...</div>

Example: A typo in a Vue binding

<img :scr="avatarUrl">

Fix: Use the attribute the message names. If a script on the page really reads an attribute with this name, write it as data-<name>, or set rule_misspelled_attribute to "ignore" for that component.

When this appears: The attribute is not one the HTML Standard lists for that element or for every element, and it is one typing slip from one that is: two neighboring letters swapped, one letter typed twice, or one letter left out, such as titel, clas, or herf. A binding such as :titel, v-bind:titel, or c-titel is checked by the attribute it sets. Letter case does not matter. Names with a hyphen or a colon, such as data-*, aria-*, or hx-*, bindings with a modifier such as .prop, component tags, custom elements, <c-element>, bindings on Vue's <slot>, and elements inside <svg> or <math> are not checked. A c-* name that looks like a misspelled directive, such as c-fro, is reported as citry.template.misspelled-directive instead. citry check --static and an editor that has not loaded your application report it too, with the severity the component's own Lint class sets as a plain string.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.misspelled-element

Misspelled HTML element. A tag looks like a typo of an HTML element, such as <dvi> for <div>. The browser renders it as an unknown element with no styles or behavior, with no error.

Message:

<{tag}> is not an HTML element. Did you mean <{suggestion}>?

Example: A typo in div

<dvi class="board">...</dvi>

Fix: Use the element the message names. If a Vue plugin registers a component with this name, set rule_misspelled_element to "ignore" for that component.

When this appears: The tag is lowercase, has no hyphen and no c- prefix, is not an HTML, SVG, or obsolete HTML element or one of Vue's built-in tags such as <component>, and is one typing slip from an HTML element: two neighboring letters swapped, one letter typed twice, or one letter left out. Any other unknown lowercase tag is not reported, because a Vue plugin may register a component under that name. Elements inside <svg> or <math> are not checked. Outside <math>, a MathML name one slip from an HTML element, such as <min>, is reported, because there it is more likely a typo of <main>. citry check --static and an editor that has not loaded your application report it too, with the severity the component's own Lint class sets as a plain string.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.unknown-aria-attribute

Unknown ARIA attribute. An aria-* attribute is not one that WAI-ARIA defines, often because of a typo such as aria-expandd. Browsers and screen readers ignore it, so the element loses the state or label it was meant to have.

Messages:

  • default:

    '{name}' is not an ARIA attribute, so browsers and screen readers ignore it.

  • suggestion:

    '{name}' is not an ARIA attribute, so browsers and screen readers ignore it. Did you mean '{suggestion}'?

Example: A typo in aria-expanded

<button :aria-expandd="open">Menu</button>

Fix: Use the ARIA attribute the message names, or the one you meant from the WAI-ARIA list. To keep a custom value on the element, store it in a data-* attribute.

When this appears: The attribute name, after any :, v-bind:, or c- prefix, starts with aria- and is not a WAI-ARIA 1.2 or 1.3 state or property. Letter case does not matter. ARIA lets no page invent its own aria-* names, so every unknown name is reported, not only typos. Component tags are not checked, because there the name is an input. citry check --static and an editor that has not loaded your application report it too, with the severity the component's own Lint class sets as a plain string.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.invalid-nesting

Element the browser moves out of a paragraph. An element that starts a new block, such as <div> or <ul>, is inside a <p>. The browser closes the paragraph before that element, so the page has a different structure from the template, and a page that Vue renders fails to compile.

Message:

<{tag}> cannot be inside <p>. The browser closes the <p> before it, so the page structure differs from the template.

Example: A div inside a paragraph

<p>Owner: <div>{{ owner.name }}</div></p>

Fix: Change the <p> to a <div>, or change the inner element to an inline one such as <span>.

When this appears: A <p> is open around the element, directly or through inline elements, custom elements, c-if, c-elif, c-else, c-for, c-empty, or a <c-slot> fallback, and the element is one that the HTML Standard says closes an open <p>: address, article, aside, blockquote, details, dialog, div, dl, dd, dt, fieldset, figcaption, figure, footer, form, h1 to h6, header, hgroup, hr, li, main, menu, nav, ol, p, pre, search, section, summary, table, ul, and obsolete ones such as center and xmp. Content inside <button>, <table>, <template>, <noscript>, <svg>, <math>, a component tag, or <c-element> is not checked, because the browser keeps it inside or the check cannot see what renders there. citry check --static and an editor that has not loaded your application report it too, with the severity the component's own Lint class sets as a plain string.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.duplicate-id

Duplicate element id. Two elements in one template always render with the same literal id. An id must be unique in the page, so a label's for attribute, aria-labelledby, URL fragments, and getElementById find only the first element.

Message:

Another element in this template already has id '{id}'. An id must be unique in the page.

Example: The same id twice

<div id="board">
  <h1 id="board">Board</h1>
</div>

Fix: Give one of the elements another id.

When this appears: Two elements have the same static id value, and neither is inside a condition or a loop: c-if, c-elif, c-else, c-for, or c-empty, as a tag or as an attribute on the element or around it; v-if, v-else-if, v-else, or v-for; a c-fill, a <c-slot> fallback, the body of a component tag, or a <template>. Those may render an element zero or several times, so the check cannot know whether both appear. v-show does not count, because a hidden element is still in the page. The same id coming from two templates is not reported. citry check --static and an editor that has not loaded your application report it too, with the severity the component's own Lint class sets as a plain string.

Default severity: error. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.missing-image-alt

Image without alt text. An <img> has no alt text. A screen reader then reads out the file name or nothing useful, and the image has no text when it fails to load.

Message:

<img> has no alt text. Describe the image in alt, or write alt="" for an image that only decorates the page.

Example: An avatar without alt text

<img src="/static/avatar.svg" width="32" height="32">

Fix: Describe the image in alt. For an image that only decorates the page, write alt="" so screen readers skip it.

When this appears: An <img> has no alt in any form (alt, c-alt, :alt, or v-bind:alt), no aria-label or aria-labelledby, and no role="none" or role="presentation". An image with a c-bind or v-bind spread is not reported, because the spread may add alt. Neither is an <img> that is a component's only top-level element, or the only element in each block of a top-level c-if, c-elif, and c-else chain, when the component may have browser code (JavaScript, js_data(), State, or event handlers), because Vue passes the alt that a parent writes on the component's tag to that element. A component whose JavaScript sets inheritAttrs: false in $component({...}) stops Vue from passing it, so that image is reported. citry check without --static, and an editor that has loaded your application, report that image when the component has no browser code or sets inheritAttrs: false. citry check --static and an editor that has not loaded your application report the other images too, but never a component's only top-level <img>, with the severity the component's own Lint class sets as a plain string.

Default severity: warning. Your application can change this severity. Reported by: citry check, citry-lsp.

citry.template.csp-incompatible

Breaks a strict Content Security Policy. The template writes something that a strict Content Security Policy blocks in the browser: an inline <script> or <style> element, an inline event attribute such as onclick, or a javascript: URL. Citry reports it only when security_csp is "warn" or "strict".

Messages:

  • Inline element:

    A strict Content Security Policy blocks this inline <{tag}>. Move it into the component's js or css, or into a Script or Style dependency.

  • Event attribute:

    A strict Content Security Policy blocks the inline event attribute '{name}'. Use a Vue listener such as @click instead, or rename a custom attribute, for example to data-{name}.

  • javascript: URL:

Default severity: warning. Your application can change this severity. Reported by: citry check.

citry.i18n.rich-message-fallback

Rich message without a translation. A <c-trans> message has no translation in some locale. Rendering it in that locale raises I18nRuntimeUnavailableError, because <c-trans> adds no element that could mark text from a fallback language.

Fix: Add a translation for each locale the finding lists. Plain text messages may fall back; only <c-trans> needs every translation.

When this appears: A <c-trans> tag names a message or attribute that has no translation in some selectable locale, so it would resolve to another locale through the configured fallbacks or the message's source locale.

Default severity: error. Reported by: citry check.

citry.i18n.client-message-invalid

Unknown client i18n message. Component.I18n.client_messages names a message that does not exist, so the browser cannot load it.

Fix: Correct the name in client_messages, or add the message.

When this appears: Component.I18n.client_messages names a message ID that no component or configured catalog package defines.

Default severity: error. Reported by: citry check.

citry.format.syntax

Invalid template syntax. The template has a syntax error, so the formatter left it unchanged.

Fix: Fix the syntax error, then format again.

When this appears: A format command receives a template with a Citry syntax error.

Default severity: error. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.suppression

Invalid formatter directive. A fmt: on, fmt: off, or fmt: skip comment has no matching partner or sits where it cannot apply.

Example: Unmatched formatter enable directive

{# fmt: on #}
<div></div>

Fix: Pair each fmt: off with a fmt: on in the same scope, or remove the stray directive.

When this appears: A formatter directive has no valid scope at the place it is written, such as a fmt: on without an earlier fmt: off.

Default severity: error. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.invariant

Formatter safety check failed. The formatter's own safety check failed, so it refused to change the file. Your template is not at fault.

Fix: The file is unchanged. Report the template and message as a Citry bug.

When this appears: The formatted result fails one of Citry's safety checks, for example formatting it a second time would change it again.

Default severity: error. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.unsupported

Formatting shape unsupported. The template is valid, but the formatter cannot rewrite this shape safely, so it left it unchanged.

Fix: Nothing to fix. Format that part by hand, or wrap it in fmt: off and fmt: on.

When this appears: The template's structure is outside what the formatter can rewrite.

Default severity: error. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.provider-invalid

Embedded formatter returned invalid output. The JavaScript or CSS formatter returned a change that does not fit the code it was asked to format, so Citry discarded it.

Fix: The file is unchanged. Try another formatter for that language, or report the message.

When this appears: An external JavaScript or CSS formatter returns an edit outside the region Citry sent it.

Default severity: error. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.embedded-suppressed

Embedded formatting suppressed. A fmt: off or fmt: skip comment kept a JavaScript or CSS region unformatted, as requested.

Fix: Nothing to fix. Remove the directive if you want the region formatted.

When this appears: A fmt: off or fmt: skip directive covers an embedded JavaScript or CSS region.

Default severity: information. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.embedded-language-unsupported

Embedded language unsupported. A <script> or <style> region declares a language Citry has no formatter for, so it was left unchanged.

Fix: Nothing to fix. Format that region with its own tools.

When this appears: An embedded script or style region declares a language that no Citry formatter handles.

Default severity: warning. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.embedded-interpolation-unsupported

Embedded interpolation unsupported. A JavaScript or CSS region contains Citry interpolation, such as {{ title }}, so it was left unchanged.

Example: Citry interpolation inside JavaScript

<script>
  const title = "{{ title }}";
</script>

Fix: Pass the value through js_data() or css_data() instead of interpolating it, or leave the region unformatted.

When this appears: An embedded JavaScript or CSS region contains Citry interpolation, which an external formatter cannot handle safely.

Default severity: warning. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.provider-unavailable

Embedded formatter unavailable. No JavaScript or CSS formatter answered, so that region was left unchanged.

Fix: In VS Code, check that Prettier for VS Code is installed and enabled for the language, or disable it so Citry uses its own copy of Prettier.

When this appears: Citry asks the editor to format embedded JavaScript or CSS, and no installed formatter returns an edit.

Default severity: warning. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.host-syntax

Invalid Python host syntax. The Python file has a syntax error, so Citry could not find the component strings to format.

Fix: Fix the Python syntax error, then format again.

When this appears: A format command targets a Python file that is not valid Python.

Default severity: error. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.ineligible

Document is not eligible for formatting. The file or cursor position is not inside a Citry template, script, or style, so there is nothing to format.

Fix: Place the cursor inside a template, js, or css string, or open the template file itself.

When this appears: Citry cannot tell that the document or cursor position belongs to a template, js, or css string, or a standalone Citry template.

Default severity: error. Reported by: citry format, citry-lsp, the Citry VS Code extension.

citry.format.stale-document

Document changed during formatting. The document changed while Citry was formatting it, so the result was discarded.

Fix: Run the format command again.

When this appears: The document changes after Citry prepares the edit and before the editor applies it.

Default severity: error. Reported by: citry-lsp, the Citry VS Code extension.

citry.format.cancelled

Formatting cancelled. Formatting was cancelled before Citry applied it.

Fix: Nothing to fix. Run the format command again if needed.

When this appears: The editor or you cancel a format request before Citry applies its edits.

Default severity: information. Reported by: the Citry VS Code extension.

Codes from the type checkers

citry.python.*

Reported by: ty. Python type errors in template expressions and c-* values, such as a value of the wrong type for a component input. They come from ty, the Python type checker Citry runs. The part after citry.python. is ty's rule name, and the message is ty's.

citry.typescript.*

Reported by: TypeScript. TypeScript errors in component JavaScript and Vue expressions, such as a wrong argument type, an unknown member, or a wrong number of arguments. The part after citry.typescript. is TypeScript's error number, such as ts2322, and the message is TypeScript's. When one of Citry's own diagnostics already reports the same mistake, Citry shows only its own.
