# Native rendering ownership: research decision

This is an analysis of a possible renderer migration, not an implementation plan or a performance claim. The current Python/Vue work should settle the semantics and representation that a native renderer would preserve; [Vue migration PR #137](https://github.com/citry-dev/citry/pull/137) need not merge or release before a bounded native proof can begin.

## Prior art and constraint

- The current [grammar, AST, compiler, and Python runtime-node pipeline](../agent/INDEX.md#the-grammar---ast---compiler---codegen-pipeline) is a linked contract. The PyO3 surface in [`citry_core_py`](../../crates/citry_core_py/src/lib.rs) already exposes the native Vue compiler, HTML transforms, safe evaluation, and i18n operations; the Python render scheduler and output assembly remain substantial.
- The archived Rust `BodyEngine` / `FoldedPlan` walked bodies but returned Python `RenderPart` objects. Its construction-bound benchmark changed **12.5 to 12.7 ms**; an earlier per-item crossing cut was **3–6% slower**. The [source and measurements](performance.md#69-postscript-the-full-engine-was-built-measured-and-archived-2026-06-25) show why moving a helper or walker to Rust while retaining the Python graph is not the target.
- This batch's [fused leaf ticket](performance_architecture_experiments.md#decision-ledger) saved 3.8% at 1,400 rows but introduced a second output type across many consumers. The Python instance-erasure proof, now the supported `simple = "vue"` mode, targeted a larger boundary. These observations motivate ownership experiments, not a forecast of Rust speed.

## Proposed host/native boundary

The native side would retain a compiled plan and own **component, loop, and effect scheduling**, selected-branch/slot relationships, occurrence and definition identities, call runs, a per-render arena (native storage owned by one render), and strict HTML/prepared-record encoding. It would emit each selected output once. A completed native record should not be mirrored as a Python `Component`, `CitryRender`, `RenderFrame`, and prepared-data graph merely to serialize it later. The internal Vue prepared representation and stable [`citry-events/1`](../../packages/protocol/events/v1/README.md) contract remain distinct.

Python still executes user callbacks and expression bytecode, supplies arbitrary mapping/object protocols, owns Django-facing Request/Response integration, and runs extension/cache hooks whose behavior cannot be certified. The native scheduler may call those Python effects through PyO3 in the required order; a Python implementation of the surrounding scheduler is not inherently required. Crossing once per text node or field would recreate the old failure. A useful prototype passes stable data or retained handles in coarse batches across the boundary, with GIL work counted in the full measurement. It must still invoke user callbacks in their existing order at each semantic dependency; batching data must not reorder effects. Exact built-in dict/list/scalar data can be copied into the native arena once. Opaque Python values remain Python-owned and require an effect barrier (a pause in native execution to call Python) or ordinary fallback. Native ownership must be real, rather than two live object graphs with synchronized lifetimes.

An optional effect contract could distinguish: **observer** hooks (still called, may have side effects, but cannot change output), **named-field mutation** hooks (called and journaled for declared fields), and **arbitrary replacement** hooks (ordinary Python rendering barrier). Applicability is per component and render phase. A static callback is not automatically pure or cacheable. A read-only data promise needs an ownership or freeze boundary, not merely a wrapper around mutable nested values. Schema factories/validators, custom attribute access, active i18n, slots/provide/inject, and cache replay also belong in admission. Unknown effects must select the ordinary path before user evaluation; no fallback may replay a callback after partial native execution.

## How to test this direction

First compare a closed, exact-source leaf and one mixed-effects fallback using the **same output mode and callback** as Python. Check complete HTML, prepared manifest, IDs and ID-generator call order, callback counts/order, dependency assets, security decisions, and source-annotated errors. Measure cold compilation and warm full `Page.render() + serialize()` with normal GC at 140/1,400 rows from a release build; record PyO3 crossings, GIL time, and arena/Python object counts. A native walk that still constructs the Python render graph, a gain confined to a synthetic markup-heavy leaf, or a regression in the full page would falsify this migration as a speed strategy. Portability alone could still justify a separate project.

No Rust benchmark has been run for this design.
