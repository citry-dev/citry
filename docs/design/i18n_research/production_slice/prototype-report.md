# Production-shaped Phase 0 i18n compiler slice

Status: the extended slice passed on 2026-08-10. It proves that the main
compiler design works through a real Rust extension and PyO3 boundary. It is
still research code, not the production i18n package.

The [runner](run_production_slice.py), [fixtures](fixtures), checked
[evidence](evidence.json), and [environment](prototype-environment.md) are the
source of truth.

## Plain-language result

Citry can keep the Fluent that developers and translators write simple. The
Rust compiler can read that source, check it, link messages from several
packages, and generate the private operations that the runtime needs. Authors
write `{ $terms_link }`; only the generated artifact contains `SLOT(...)`.
Authors write normal Fluent plural and ordinal choices; only the generated
artifact contains `CITRY_PLURAL(...)`.

The same compiled extension now handles the broader behavior that the earlier
Python compiler spike proved:

- cardinal and ordinal choices;
- exact-number branches;
- named `NUMBER` and `DATETIME` profiles;
- public message references and layer-private terms;
- input types inherited through public references;
- one rich Slot used more than once; and
- exact source ranges for every generated operation.

Python passes typed values to Rust with tagged JSON records. The proof kept the
integer `9007199254740993`, the decimal `9007199254740993.25`, signed decimal
zero, and an offset-aware date-time string intact. It rejected a wrong tag, a
non-canonical or non-finite decimal, a date-time without a zone, a bad Slot
marker, bidi controls, and paragraph boundaries before Fluent evaluated the
message.

Actual Citry components still reached the runtime through template `tr()`,
`self.i18n.tr()`, and an ordinary transparent `<c-trans>` component. No new
rich-message grammar or special AST node was needed.

## What passed

### The positioned Rust parser works inside the real compiler

The compiler now parses each catalog with the positioned `Slice` type proved
by the semantic-span exploration. Each identifier and source fragment keeps
its UTF-8 byte range. The compiler uses those ranges while it generates the
linked artifact.

The checked artifact contains 44 operation maps. They cover scalar inputs,
Slots, public references, private terms, cardinal selectors, ordinal selectors,
number formatting, and date-time formatting. The runner reopens every authored
and generated byte range and confirms that it points to the expected operation.
Repeated occurrences of the same Slot have separate ranges.

This replaces the old `entry-start-only` result. Exact semantic positions are
no longer an open question for the tested compiler subset.

### Normal Fluent can generate Citry's private operations

The fixture catalogs contain no `CITRY_*` or `SLOT` calls. The Rust compiler
adds these operations to the linked artifacts:

- a displayed string becomes `CITRY_TEXT($value)`;
- a displayed rich value becomes `SLOT($fill)`;
- a numeric selector becomes `CITRY_PLURAL(...)`;
- `NUMBER($value, type: "ordinal")` in selector position becomes an ordinal
  plural operation; and
- named `NUMBER` and `DATETIME` profiles remain explicit formatter calls.

The compiler rejects a numeric or date-time value displayed without its
formatter, an unsupported selector type, and a formatter call without a
literal profile. It also rejects an authored `SLOT(...)` call and fails closed
on expression shapes outside this slice.

### Repeated Slots use a path rule, not a maximum count

Each reachable selector branch must contain every required Slot. A branch may
use the same Slot any number of times. The positive fixture uses one link twice
in each branch. A negative fixture removes it from one branch and fails
compilation.

The runtime receives one opaque marker for the named fill. If the translation
uses that variable twice, the marker appears twice, so Citry can invoke the
repeatable Slot twice. This proves compiler and server-render behavior. It does
not yet settle browser DOM identity or focus when a client-side locale switch
moves repeated rich content.

### The typed Python-to-Rust wire keeps exact values

The tested wire uses `{type, value}` records. It supports `str`, `int`,
`Decimal`, `datetime`, and `Slot` for this slice. Integers and decimals travel
as canonical strings, so they do not pass through an imprecise JSON number.

The runtime checks the record against the message contract before it builds
Fluent arguments. This prevents a value labeled as one type from entering a
different formatter or selector path.

Because the artifact and argument contract changed, the research artifact
schema is now version 2. Both the compiler and runtime reject the earlier
version instead of trying to read it as the new shape.

The final browser wire still needs more types and stronger date/time records.
This proof only establishes that an exact tagged boundary is practical across
Python and PyO3.

### Bidi checks happen before message evaluation

The compiler rejects literal bidi controls and Fluent `\uXXXX` or `\UXXXXXX`
spellings that decode to a bidi control. The runtime rejects bidi controls and
paragraph boundaries in scalar inputs before `CITRY_TEXT` isolates them.

The slice does not yet attach the selected fallback language and direction to
rich output. It also does not prove the final whole-message, multi-paragraph
isolation policy. Those remain separate browser and accessibility gates.

### Package linking and incremental parsing still work

The larger fixture still proves all results from the earlier reduced slice:

- an application can override a `citry_ui` message without taking ownership;
- values and attributes can select different layers;
- an incomplete locale graph falls back as one graph to the defining
  package's source locale;
- two packages can have different source locales;
- public references inherit typed inputs; and
- private terms stay with the layer that defines the selected message.

The first compile parsed four catalogs. The warm compile reused all four.
Changing one catalog reparsed one and reused three. Reversing discovery order
produced the same revision and manifest.

### The real Citry API proof still passes

The integration proof still uses current Citry behavior:

- `on_component_data()` supplies template `tr`;
- nested extension config supplies `self.i18n` and
  `Component.I18n.client_messages`;
- inline `messages` and file-backed `messages_file` reuse the current asset
  loader and watcher index; and
- `<c-trans>` remains an ordinary transparent component with named fills.

The V3 parser still distinguishes a direct literal `tr()` call from a composed
or dynamic call and retains the component/fill source positions.

## Other finding

The old evidence hashed `citry_i18n_phase0/__init__.py` and called it the
extension binary. That file is only the package initializer, so its digest
could stay unchanged while Rust changed. The runner now records both the
initializer and the actual compiled `.so` separately. The executable used by
the old proof was current, but its identity label was wrong.

## What remains open

This slice deliberately stops before these Phase 0 questions:

- The plural rules and formatter text in this crate are deterministic test
  implementations. The final runtime must use the selected CLDR-backed service
  and named profile mappings.
- The tagged wire needs the rest of the planned number, date, time, local
  date-time, instant, zone, and formatter-wrapper types.
- Browser delivery, artifact validation, locale switching, DOM ownership,
  focus, and repeated Slot identity are not exercised.
- Rich Slots still need explicit language and direction ownership.
- Fallback-language metadata and whole-message paragraph isolation are not
  exercised.
- `messages` and `messages_file` still use a private loader rather than a real
  fourth core asset pair.
- The provider, canonical locale map, cache token, and cache replay rules still
  need their own production-shaped proofs.
- The checked server timings now include the required 100 message resolutions
  and 20 named formatter calls. They still use the deterministic formatter
  stand-in. Large catalogs, the final ICU4X adapter, Linux, wheel targets, and
  browser payloads remain outside this slice.

## Decision

Keep the Rust compiler/linker plus thin PyO3 architecture. The positioned
`fluent-syntax` route is good enough for exact diagnostics and source maps, so
Citry does not need a second parser or a fork for this subset.

Keep normal authored Fluent, generate `SLOT` and `CITRY_*` only inside compiled
artifacts, allow a Slot more than once, and require it at least once on every
reachable path.

The later rich-message, provider, cache, backend, and Phase 0 completion slices
use this compiler result. Their combined result is summarized in the main i18n
design and the Phase 0 completion report.
