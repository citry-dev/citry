# Content-port audit: DJC content pages ported vs skipped

Companion to [`docs_site_parity_audit.md`](docs_site_parity_audit.md). That doc audits the 228 *feature* rows; this one audits the **content pages** specifically: for every one of the 52 markdown files under DJC's `content/docs/`, what happened to it in citry. Produced 2026-07-03 by reading each DJC file (max-effort per-file classification) and checking it against citry's `docs_site/content/`. Regenerate the same way when content moves.

## Headline

Of **52** DJC content pages:

| Disposition | Count | Meaning |
|---|---|---|
| Ported | 44 | Topic covered by a citry page (adapted to citry's model). |
| Partial | 0 | A citry page covers part of it; real content is missing. |
| Dropped (not applicable to citry) | 8 | Genuinely Django-specific. |
| **Skipped (real gap)** | **0** | Topic applies to citry but no page covers it. |

Workstream A (2026-07-03) closed every content gap then present. **Phase 1** ported 17 of the 18 skipped pages as 16 new citry pages (`secondary_js_css_files` and `adding_dependencies` merged; `upgrading/v0.md` dropped). **Phase 2** enriched the 12 real partial pages into 8 existing target pages (several DJC sources map to one citry page), each addition grounded in the real citry source, render-verified, and preservation-checked against the pre-edit page. Cache Phase 5 (2026-07-23) subsequently ported `component_caching` into the existing `advanced/caching.md` guide after Citry gained both `Component.Cache` and `<c-cache>`. The earlier content port was a good scaffold (getting-started, syntax, core concepts); workstream A added the community section, the advanced concepts, the guides, and the about pages, and then filled in typing, rendering, slots, provide/inject, extensions, the JS/CSS pages, and the home-page highlights.

## Dropped - not applicable to citry, correctly not ported

All eight are Django-specific.

| DJC page | Why it does not apply to citry |
|---|---|
| `concepts/fundamentals/component_views_urls.md` | Built entirely on Django's View: Component.as_view(), Django urlpatterns, get/post handlers, render_to_response() returning HttpResponse, and get_component_url(). citry has no component-as-HTTP-endpoint (its 'class View:' is a generic extension-config hook, not HTTP handlers); the user need (serve a component's HTML over HTTP) is met instead by the framework-agnostic mount (web-frameworks.md) plus HTMX-style fragments (advanced/html-fragments.md), which are already documented. |
| `concepts/fundamentals/http_request.md` | Entirely Django request plumbing: RequestContext vs Context, passing Django's HttpRequest into render(), Component.request, Django context processors, and csrf_token. citry has no built-in Component.request or context-processor system; request-scoped data (current user, request id) is threaded via provide/inject (concepts/provide-and-inject.md, which even uses 'a request object' as its example) or template_globals, both already documented. |
| `concepts/advanced/component_registry.md` | The file is Django's @register decorator + ComponentRegistry bound to a Django Library via {% load %}, plus tag_formatter/RegistrySettings; citry has none of that - components auto-register when defined with `citry = app` and resolve as <c-Name>, and the surviving concepts are already covered incidentally. |
| `concepts/advanced/tag_formatters.md` | Entirely about reformatting the Django {% component %}/{% endcomponent %} template tags via COMPONENTS.tag_formatter (e.g. shorthand {% button %}...{% endbutton %} through TagFormatterABC.parse over {% %} tokens); citry's HTML-like <c-name> syntax has no {% %} tag to reformat and ships no TagFormatter equivalent. |
| `concepts/advanced/template_tags.md` | A guide to authoring custom Django template tags via @template_tag/BaseNode registered on a Django Library (node/context/nodelist/{% mytag %}); citry exposes no such Python tag-registration API (built-in <c-*> tags live in the Rust grammar), and the equivalent user need - a reusable, typed tag that accepts a body/slots - is served by Components, already documented in getting-started and concepts (components, typing-and-validation, slots). |
| `overview/security_notes.md` | Entirely Django static-files security (the safer_staticfiles drop-in app, collectstatic, STATICFILES_DIRS vs COMPONENTS.dirs exposure of .py/.html files); citry serves component assets through mounted routes (/{prefix}/asset/...), not Django's staticfiles collector, so none of it applies. citry's own /security/ page is a different topic (the expression sandbox), not a port of this. |
| `migrating_from_safer_staticfiles.md` | Entirely Django staticfiles configuration (removing django_components.safer_staticfiles from INSTALLED_APPS, STATICFILES_FINDERS/ComponentsFileSystemFinder, COMPONENTS.dirs vs STATICFILES_DIRS, collectstatic pipeline); citry's framework-agnostic web layer has no Django staticfiles machinery, so none of it applies. |
