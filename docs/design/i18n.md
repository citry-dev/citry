# Design: internationalization and localization

**Status:** Phase 0 exploration is complete. The production server now has the
checked compiler and linker, typed message operations, selected ICU4X format
profiles, standalone catalog packages, locale fallback, server `<c-i18n>` and
`<c-trans>`, plain cache-variation data, and project commands. Strict localized
number editing, package-owned time-zone conversion, and time/datetime profiles
are also implemented. Browser-side locale switching, Citry UI migration, date
editing, and percent/unit profiles remain open.

**Research date:** 2026-08-11.

**Applies to:** the Python `citry` runtime, its built-in `i18n`
extension and template surface, application components, and `citry-ui`.

## Current implementation

The server implementation reached its first production-shaped slice on
2026-08-11. It includes:

- an always-installed but dormant built-in `i18n` extension;
- strict ICU4X locale parsing, CLDR alias canonicalization, and direction lookup
  through the existing Rust/PyO3 extension;
- immutable `LocaleContext` values passed into a render through the ordinary
  root provide mapping;
- strict engine settings for the source, default, and allowed locales,
  fallback graphs, ordered plain-string catalog package names, and named format
  profiles;
- `Component.I18n.client_messages` validation, `self.i18n.context`, text-only
  `tr()`, and typed `self.i18n.format` / template `fmt` helpers;
- `messages` / `messages_file` as a fourth primary asset pair, including lazy
  loading, inheritance, file watching, atomic last-valid reload behavior,
  extension hooks, and component introspection;
- a language-neutral Rust `citry_i18n` compiler and runtime using
  `fluent-bundle` 0.16.0, with typed parameters, public references,
  source-unit-local private terms, string and plural selectors, exact-number
  branches, parameter descriptions and declaration spans, source maps,
  diagnostics, rich Slot markers, and deterministic revisions;
- locale-major resolution across ordered application and package layers,
  followed by the defining package's source locale. Values and attributes are
  resolved separately, and the selected locale controls plural and formatter
  behavior;
- ICU4X 2.2 named profiles for exact decimal numbers, currencies, dates,
  wall-clock times, aware datetimes, day-based relative time, and
  conjunction/disjunction lists. Unsupported profiles fail when the engine is
  configured. Currency formatting uses CLDR
  minor-unit digits and half-expand rounding rather than preserving the input's
  accidental number of decimal places;
- strict number editing through the same named `NumberFormat` profile used for
  display. It accepts the locale's resolved digits, signs, decimal separator,
  grouping separator, and grouping sizes, and returns separate `valid`,
  `incomplete`, and `invalid` states without discarding the edit string;
- time-zone conversion from exact aware Python datetimes. Citry opens its
  pinned `tzdata` package directly, records the package version and database
  digest in `LocaleContext`, and never reads the host machine's zone database;
- standalone package loading from `citry-i18n.toml` and canonical
  `locales/<locale>/**/*.ftl` resources, plus checked production manifests,
  source-free linker input, and final server artifacts;
- `citry ext run i18n extract|check|compile|inspect` project and package
  commands, plus project-wide checks for unknown literal outputs, typed `tr()`
  arguments, `<c-trans>` values and fills, client-message outputs,
  cross-language plain-text fallback, and missing parameter types;
- ordinary server components `<c-i18n>` and `<c-trans>`. The provider can be
  transparent or emit a real `lang` / `dir` host; rich messages escape catalog
  text and keep application fills structural, including repeated fills; and
- a plain immutable i18n context identity that authors may put into ordinary
  `Cache.vary()` or `<c-cache vary>` data. Cache has no i18n-only fields,
  arguments, imports, or branches.

The boundary is deliberate. `client=True` reports that browser switching has
not shipped yet. Percent, unit, and date editing still fail instead of silently
using weaker behavior. Time-only formatting accepts wall-clock fields and no
zone. Datetime formatting requires an aware instant and an explicit time zone
in the provided context.
Production catalog packages are checked against generated artifacts, then the
application links their checked semantic records into its own layer and
fallback graph without reopening package FTL. Client artifacts are later work.

## 1. Decision summary

Internationalization is not only translation. Citry needs one coherent locale
context shape, with one immutable resolved context instance per render tree or
overridden subtree. This is not one process-global singleton. The resolved
instance coordinates five related but independently testable capabilities:

1. Message selection and translation, including plural, grammatical, and
   accessibility variants.
2. Locale selection, canonicalization, fallback, and render-root or subtree scope.
3. Formatting of numbers, currencies, percentages, dates, times, time zones,
   lists, relative times, and units.
4. Text direction and bidirectional-text safety, including `lang`, `dir`,
   logical layout, and component-specific icon mirroring.
5. Locale-aware parsing and comparison where an interactive control requires
   them. Parsing is a separate contract from formatting and starts later.

The leading proposal is a built-in extension named `i18n`, installed on every
`Citry` engine like Cache, Dependencies, and Events but dormant until
configured. Its close integration points are component assets, render context,
template expressions, cache keys, dependency emission, and tooling. The Rust
extension owns the selected Fluent message runtime and ICU4X locale data. The
browser uses its built-in ECMA-402 `Intl` formatters plus the checked Fluent
client runtime only inside an explicit client-switching boundary.

`citry-ui` remains usable when i18n is unconfigured. Every library-authored
string keeps a typed explicit override and an English source default. When
i18n is configured, the same default is resolved by a stable message ID,
and application catalogs may override the library layer without forking the
component.

The selected message format is Fluent FTL because it supports private
terms, message attributes, translator-controlled selectors, and CLDR plural
categories. Rust `fluent-bundle` 0.16.0 is the selected server message runtime,
and the browser uses `@fluent/bundle` 0.19.1 where client switching is enabled.
Typed number and date formatting uses ICU4X behind Citry's named server
profiles and ECMA-402 `Intl` in the browser. Each named profile still has to
pass its declared cross-runtime contract before it can ship.

The first delivery is server-first: a request selects one locale, SSR resolves
matching `lang`, `dir`, messages, and formats for the application document
shell, and a locale change may use normal navigation. Reactive in-page
switching is a later enhancement with a stricter artifact and ownership
protocol. It is not an initial correctness dependency.

### 1.1 From authored messages to runtime lookup

The high-level flow is:

```text
component messages + standalone catalog packages
    -> parse each Fluent source unit
    -> inventory messages, attributes, variables, terms, references, selectors,
       variants, function calls, rich Slots, comments, parameter types,
       and exact source ranges
    -> assemble one deterministic in-memory project catalog graph
    -> validate ownership, IDs, references, types, call sites, and fallbacks
    -> compile versioned server and browser artifacts plus source maps
    -> resolve one message from those artifacts for the active locale
```

This does not concatenate every authored block into one large FTL file. Each
component or standalone catalog remains a traceable source unit. The project
graph records which package and source unit defines every public message ID,
which private terms belong to that unit, and how references connect them. The
graph is what lets `check` reject a duplicate ID or an unknown literal
`tr("...")` key even when the definition and use are in different components.

The type of a Fluent variable is local to one message contract, not to a file,
component, or whole catalog. One message contract includes its value and all
its attributes. Therefore two unrelated messages may both use `$name` with
different types, while a value and attribute belonging to the same message
share one `$name` type. References can make a caller depend on another
message's parameters; Citry computes that dependency explicitly rather than
turning the variable name into a global declaration.

The batch commands build the graph directly from discovered component classes,
their `messages` / `messages_file` assets, and configured package manifests.
`extract` writes translator-facing files from that graph, but a previously
extracted file is not a prerequisite for `check`. An editor uses the same graph
as a live project index and reports unknown keys only after discovery for the
relevant project is complete.

### 1.2 The private `CITRY_*` and `SLOT` operations

Application authors and translators write normal Fluent. They never write
`CITRY_TEXT`, `CITRY_PLURAL`, or `SLOT`. These names are private instructions
that Citry puts into the checked, compiled catalog when the released Fluent
runtimes do not expose the control point Citry needs.

The flow looks like this:

```text
authored Fluent
    -> Citry parses and checks it
    -> Citry generates private runtime instructions where needed
    -> Fluent resolves the message
    -> Citry turns the result into safe text and structural Slot instances
```

For example, an author writes:

```ftl
account-greeting = Welcome, { $name }.
terms-acceptance = Read { $terms_link } before continuing.
```

The source contract tells Citry that `$name` is text and `$terms_link` is a
rich `Slot`. The compiled artifact may then contain the equivalent of:

```ftl
account-greeting = Welcome, { CITRY_TEXT($name) }.
terms-acceptance = Read { SLOT($terms_link) } before continuing.
```

The three operations have separate jobs:

- `CITRY_TEXT` keeps the boundary around one application value long enough for
  Citry to check unsafe bidirectional controls and isolate that value from the
  surrounding sentence. Fluent normally joins everything into one string, so
  the boundary would otherwise be lost.
- `CITRY_PLURAL` chooses a selector key such as `exact-0`, `one`, `few`,
  `many`, or `other`. Citry generates it for plural selectors so cardinal and
  ordinal rules, exact-number branches, the selected catalog locale, and
  precise values behave the same on Python, Rust, and the browser. It chooses a
  branch; it does not produce user-visible wording.
- `SLOT` temporarily replaces one application-owned rich Slot with a fresh,
  unguessable text marker. If a translation uses the Slot twice, the marker
  appears twice. After Fluent finishes, Citry finds each occurrence and creates
  a separate rendering of the original lazy Slot at that position. The marker
  never reaches the final HTML or DOM.

These particular names are implementation details, not permanent public API.
If a future Fluent runtime exposes structured values, selector hooks, and rich
placeholders directly, Citry may replace them without changing authored FTL or
application templates. The important contract is that the compiler owns these
steps and every generated operation points back to the original source range.

## 2. Terminology and scope

### 2.1 i18n and l10n

The abbreviations count the omitted letters:

- **Internationalization, i18n:** engineering a product so it can adapt to
  different locales without changing product source code.
- **Localization, l10n:** creating and validating the actual locale-specific
  adaptation, such as Czech messages, Arabic layout review, or Japanese date
  conventions.
- **Locale:** a bundle of user-facing conventions. A locale identifier commonly
  contains language and may add script, region, calendar, numbering-system, or
  other Unicode extensions. It is not a country and does not imply a time zone.
- **Locale canonicalization:** validate one locale identifier and rewrite
  aliases, casing, and extension ordering to one standard BCP 47
  spelling. For example, `cs-cz` becomes `cs-CZ` and the deprecated language
  alias `iw-IL` becomes `he-IL`. Canonicalization does not guess a region:
  turning `en` into `en-US` is locale matching or likely-subtag expansion, a
  separate policy. Citry's core API is strict: legacy underscore input such as
  `en_US` is rejected rather than silently rewritten. An HTTP/framework adapter
  may offer a separately named legacy-normalization step before calling core.
- **Translation:** replacing or restructuring natural-language messages. It is
  one part of localization.
- **Catalog compilation:** Citry parses authored FTL, checks it, and generates
  the internal runtime form and source maps. The proposal uses the concrete
  verbs parse, check, rewrite, compile, and generate for each step.

Citry accepts canonical Unicode locale identifiers based on BCP 47, such as
`en-US`, `cs-CZ`, `sr-Latn`, or `ar-EG`. CLDR describes the relationship between
BCP 47 tags and Unicode locale identifiers in
[Unicode TR35](https://www.unicode.org/reports/tr35/tr35.html#BCP_47_Conformance).

### 2.2 Capability boundary

| Capability | In the i18n feature? | Initial delivery |
|---|---|---|
| Messages, variables, plurals, selects, fallback | Yes | Required |
| Locale resolution and scoped locale changes | Yes | Required |
| Numbers, currencies, percentages, dates, times, lists, relative time, units | Yes | Added profile by profile; an unproved category fails clearly instead of guessing |
| `lang`, `dir`, RTL/LTR layout, bidi isolation | Yes | Required |
| Locale-aware number input and date/time control display | Yes | After the formatter foundation |
| Locale-aware parsing | Yes, where controls need it | Strict numeric parsing first; arbitrary natural-language date parsing is excluded |
| Collation, search, segmentation, case mapping | Yes, when a component claims locale-aware behavior | Follow-up capability, with Combobox as the first likely consumer |
| Time-zone conversion and DST presentation | Formatting yes; business scheduling no | Explicit zone formatting only at first |
| Translation management system integration | Tooling ecosystem, not core runtime | Later adapters |
| Machine translation | No | Applications or external tooling own it |
| Localized routes, SEO, regional legal/content policy | No automatic framework behavior | Applications own it |

Locale-aware parsing is the inverse boundary needed by editable controls. A
user may enter `1.234,56`, `1,234.56`, Arabic-script digits, or an ambiguous
date such as `04/05/2026`; the control uses its resolved locale and an explicit
input contract to turn the edit string into a canonical `Decimal`, `date`, or
other domain value. Formatting a value and parsing an in-progress edit are
separate APIs because a control must also represent incomplete and invalid
states without corrupting the canonical value.

Parsing uses named profiles, but it does not run the formatter backwards. A
`NumberFormat` profile now defines both how a number is displayed and the
strict editing grammar accepted by `self.i18n.parse.number(...)`. The locale in
the provided context supplies the actual digits and separators. The profile
name keeps a control's display and parsing policy together while the two APIs
remain separate. Date editing will follow the same rule, but it still needs an
explicit numeric-field, calendar, and ambiguity contract; a formatted date
string is not automatically parseable.

Direction and translation are coordinated by one locale context but are not
the same mechanism. **LTR/RTL** is the base direction assigned to a document,
element, or paragraph. **Bidirectional text**, or bidi, is the Unicode ordering
behavior inside mixed-direction content, such as an Arabic sentence containing
an email address, product code, number, or English name. **Bidi isolation**
places an interpolated run in its own directional boundary, using semantic
markup such as `<bdi>` / `dir="auto"` or Unicode isolate controls, so its
characters and punctuation cannot reorder the surrounding sentence. An
application can render English text in an RTL subtree or Arabic text inside an
LTR document, so direction has an explicit override and is emitted as semantic
markup, not inferred only by CSS.

## 3. Citry prior art and constraints

This proposal reuses existing contracts rather than introducing a second
component or ownership model.

### 3.1 Prior art

- [`extensions.md`](extensions.md) establishes per-`Citry` extension instances,
  built-in extensions, per-component extension config, lifecycle hooks, and
  commands. I18n follows that model while adding a primary message asset pair
  because messages are authored content analogous to templates, JS, and CSS.

  or file-backed primary asset pairs. `messages` / `messages_file` is proposed
  as the fourth pair, with the same declaration-site path, inheritance, cache,
  watcher, and invalidation rules.
- Application lint severities already use `"ignore" | "warning" | "error"` in
  [`settings.py:61-112`](../../packages/py/citry/citry/settings.py), and
  [`component.py:700-710`](../../packages/py/citry/citry/component.py) exposes
  C3-composed per-component `Lint` overrides. The effective-policy records and
  application/component merge live in
  [`_linting.py:165-212`](../../packages/py/citry/citry/_linting.py) and
  [`_linting.py:276-360`](../../packages/py/citry/citry/_linting.py). The
  missing-parameter-type rule extends that existing mechanism rather than
  introducing a separate i18n severity system.
- [`caching.md`](caching.md) already requires localized output caches to vary by
  ambient locale or catalog revision. It also distinguishes compiled-template,
  output, fragment, and constant-body caches.
- [`alpinejs.md`](alpinejs.md) and the implemented `provide()` / `inject()` plus
  `$provide()` / `$inject()` contracts give locale context one ownership path
  across server rendering, slots, retained DOM, morphs, and teleports.
- [`ui_library_plan.md`](ui_library_plan.md) promises application-supplied text
  and inherited LTR/RTL today, while deferring a complete localization layer.
  This document is that follow-up.
- [`ui_component_inventory.md`](ui_component_inventory.md) blocks date, time,
  calendar, date-range, and locale-sensitive number controls on parsing,
  formatting, time zones, locale resolution, direction, and server/browser
  agreement.

### 3.2 Constraints that shape the design

1. A `Citry` object may serve concurrent requests. Locale and time zone cannot
   be mutable process-global fields on the extension.
2. Components are server rendered and may continue behavior in the browser.
   The browser must receive the same resolved locale, direction, message
   contracts, and named format profiles as the server.
3. Application components and packaged libraries share a registry. Catalog
   identity and override precedence must be deterministic across wheels.
4. Authoring UX decides whether i18n needs a normal template global, a built-in
   tag, or a V3 grammar change. Parser implementation cost is evidence in the
   prototype, not a reason to start with an inferior API.
5. The built-in integration should be small and dormant when unconfigured.
   Whether its message runtime and CLDR data ship unconditionally depends on
   measured package size, maintenance, and parity rather than a preset package
   boundary.
6. Localized HTML is a security boundary. Translation files cannot inject raw
   trusted markup or executable attributes.
7. I18n metadata crosses the active V3 Rust/Python boundary. The load-bearing
   prior art is exact:

   - [`grammar.pest:245-271`](../../crates/citry_template_parser/src/grammar.pest)
     parses components through ordinary HTML tags, while
     `template_expression` at `grammar.pest:391-395` already accepts a normal
     `tr(...)` Python expression.
     [`grammar.rs:1-5`](../../crates/citry_template_parser/src/grammar.rs)
     derives the one `GrammarParser` from that file. No new Pest form is needed
     for either API.
   - [`ast.rs:21-35`](../../crates/citry_template_parser/src/ast.rs) defines the
     source-bearing `Token`; `Expr` at `ast.rs:549-565`, `Node` at
     `ast.rs:627-665`, and `TemplateElement` at `ast.rs:850-857` are the AST
     records whose shape would change if literal-call metadata is stored there.
   - [`parser.rs:92-137`](../../crates/citry_template_parser/src/parser.rs)
     enters through `parse_template`; `process_template_expression` and
     `process_expression` at `parser.rs:498-565` retain expression and variable
     spans. Fill placement is validated by `validate_fill_placement` beginning
     at `parser.rs:1780`.
   - [`compiler.rs:17-40`](../../crates/citry_template_parser/src/compiler.rs)
     names the emitted runtime-node signatures. `compile_template_body` at
     `compiler.rs:172-230` emits `ExprNode`, and `compile_component_node` at

   - [`lang/lang.rs:38-51`](../../crates/citry_template_parser/src/lang/lang.rs)

8. Plain `tr()` is ordinary Python expression syntax, and `<c-trans>` is an
   ordinary built-in component call with named fills. Neither needs a new Pest

   shape and the complete binding blast radius before implementation.

## 4. External research

The survey uses maintained official documentation and tagged source where the
public guide does not expose enough implementation detail. Its purpose is to
identify durable patterns, not to copy one ecosystem's API.

package records: [Vue I18n 11.4.8](https://registry.npmjs.org/vue-i18n/latest),

FormatJS emphasize scoped runtime providers, Angular emphasizes extraction and
per-locale builds, and Paraglide emphasizes compiled typed functions and
request strategies. Citry should cover scope, fallback, typed formatting,
tooling, and payload control without claiming that every framework supplies all
five in the same layer.

#### Vuetify deep dive

Vuetify is the closest comparison for the boundary between an application i18n
system and a styled component library:

1. `createVuetify` constructs locale and date instances separately. Locale owns
   reactive `current`, `fallback`, messages, translation, number formatting,
   and subtree providers. Date owns a replaceable adapter and watches the
   current locale through a locale-code map. See Vuetify's tagged
   [framework construction](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/framework.ts),
   [locale contract](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/composables/locale.ts),
   and [date contract](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/composables/date/date.ts).
2. The built-in translator interprets `$vuetify.*` strings as keys and other
   strings as literals. Components can therefore have a catalog-backed default
   while a caller passes a direct string. Lookup tries the current locale, then
   configured fallback, then emits the key with console diagnostics. See the
   [built-in adapter](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/locale/adapters/vuetify.ts).
3. The English catalog is component-shaped, including date-picker and
   data-table accessibility groups, pagination labels, validation rules, and
   parameterized entries. It is an inventory of library-authored output, not a
   general application catalog. See the
   [English catalog](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/locale/en.ts).
4. Vuetify can adapt to Vue I18n or a custom `LocaleInstance`. This lets an
   application choose its broader message system while Vuetify retains stable
   internal keys. See the
   [Vue I18n adapter](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/locale/adapters/vue-i18n.ts).
5. RTL is a direction map and component class concern. Tagged source does not
   set document `lang` or `dir`, so the application still owns semantic document
   attributes. Citry should make that owner explicit rather than relying on
   component CSS alone.

Tagged source also shows why provider contracts need behavioral tests. In
4.1.8, `VLocaleProvider` declares `fallbackLocale`, while both adapter-provider
paths read `fallback`; and a custom RTL map replaces rather than extends the
built-in map. These are source-backed observations, not documented guarantees.
See the [provider props](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/components/VLocaleProvider/VLocaleProvider.tsx)
and [`createRtl`](https://github.com/vuetifyjs/vuetify/blob/v4.1.8/packages/vuetify/src/composables/locale.ts).

The UI-library pattern is deliberately narrower than an application i18n
framework. A library owns the strings and locale-sensitive behavior that it
authors, exposes global or subtree defaults, and lets the application override
individual component text. It should not replace the application's message
catalog for product copy.

### 4.3 Python server-side runtime

Python has no single standard-library equivalent of the browser's `Intl`
object. The relevant standard modules are deliberately narrower:

- [`locale`](https://docs.python.org/3/library/locale.html) wraps the platform C
  locale. Its active locale is process-global and `setlocale()` is not
  thread-safe on most systems, so Citry cannot use it for concurrent
  request-scoped formatting.
- [`gettext`](https://docs.python.org/3/library/gettext.html) loads translated
  message catalogs but is not a general locale formatter, parser, direction,
  or canonicalization service.
- [`zoneinfo`](https://docs.python.org/3/library/zoneinfo.html) supplies IANA
  time-zone arithmetic and DST behavior. It intentionally uses either system
  data or the first-party `tzdata` package and does not localize the resulting
  values.

The closest pure-Python formatting baseline is
[Babel](https://babel.pocoo.org/en/latest/api/). Babel 2.18.0
[uses CLDR 47 and reports its CLDR version](https://babel.pocoo.org/en/latest/changelog.html#version-2-18-0).
It covers the initial number, currency, date/time,
list, relative-time, unit, plural, strict decimal parsing, and limited date/time
parsing surface. It does not provide the whole `Intl` surface: collation, segmentation,
full locale canonicalization, and an explicit general alternate-calendar API
remain gaps. Its `numbering_system` option changes symbols but does not shape
ASCII digits into locale digits: even Arabic and Devanagari profiles retain
ASCII digits. Babel therefore cannot pass Citry's non-ASCII-digit matrix unless
the prototype adds and validates a separate shaping layer.

Babel 2.18.0 is the small comparison backend for its supported profile subset,
not the production backend. Installing a pinned `tzdata`
wheel is insufficient by itself because `zoneinfo` normally prefers system
`TZPATH`. A reproducible deployment must select one data source at process
start, such as `PYTHONTZPATH=""` for package-only data, record its version or
digest, and prohibit request-time `reset_tzpath()` mutation.

[PyICU](https://pypi.org/project/PyICU/) exposes the much broader ICU surface,
including canonicalization, collation, segmentation, calendars, formatters,
and parsers. It is the full-capability comparison candidate, but it is a native
binding whose source build needs ICU libraries and headers, and its observable
data versions depend on the linked ICU installation. The prototype must measure
that packaging and deployment cost rather than assume it fits Citry's default
install.

The bounded formatter comparison is recorded in
[`i18n_research/formatter_backend/prototype-report.md`](i18n_research/formatter_backend/prototype-report.md).
Babel matched plural behavior and ordinary Latin-digit profiles, but it did not
shape or strictly parse the tested Arabic-Indic and Devanagari digits, accept the
tested Unicode locale extension, or produce the Buddhist calendar year. PyICU
and Node `Intl`, both on ICU 78.3, shaped the digits, honored the Buddhist
calendar, matched plural categories, and accepted an exact decimal string beyond
the binary64 safe-integer range. PyICU also parsed all four tested digit-system
inputs; `Intl` exposes no number parser.

That does not make raw PyICU a drop-in browser twin. The two ICU 78.3 APIs still
differed in Russian whitespace and in `az-Arab` service fallback. Projecting the
latter to Azerbaijani base-language service data reproduced the browser output,
but Citry may not generalize that observation into blind script stripping. It
needs a versioned locale-to-service-locale rule, explicit calendar and numbering
profiles, and per-profile semantic or bounded presentational parity tests.
That comparison left PyICU as the capability-fit candidate with native
packaging cost and Babel as the subset candidate. The later ICU4X exploration
selects a different production foundation below; Babel and PyICU remain useful
oracles.

Locale canonicalization, direction, matching, and fallback should not differ
between the Python runtime and Rust template/tooling code. The leading shared
implementation candidate is Rust
[`icu_locale`](https://docs.rs/icu_locale/latest/icu_locale/), whose
`LocaleCanonicalizer`, `LocaleDirectionality`, and `LocaleFallbacker` keep those
policies in one versioned core. Canonicalization remains distinct from likely-
subtag expansion, negotiation, fallback, and time-zone selection.

The official Python [`fluent.runtime`](https://pypi.org/project/fluent.runtime/)
is useful prototype material but cannot be adopted on name alone: its current
0.4.0 package is classified Alpha, was released in 2023, advertises Python only
through 3.9, and documents gaps in number and date options. The prototype must
also compare the maintained Rust
[`fluent-bundle`](https://docs.rs/fluent-bundle/latest/fluent_bundle/) path or a
small Citry-owned binding before ratifying Fluent on the server.

The second bounded Phase 0 spike is recorded in
[`i18n_research/runtime_backend/prototype-report.md`](i18n_research/runtime_backend/prototype-report.md).
It obtained identical normalized term, attribute, selector, formatter,
illustrative linked-artifact, and rich-marker output from `fluent.runtime`
0.4.0, `@fluent/bundle` 0.19.1, and `fluent-bundle` 0.16.0 for hand-generated
English and Czech fixtures. It covered Czech fractional `many`, English
ordinals, hostile bidi controls, random rich markers, and optimized Python
execution. That keeps Fluent viable but does not prove the authored-to-generated
compiler or ratify a production combination. Released `fluent.runtime` fails
the release-age and advertised-Python-support gates; Rust remains the leading
server candidate, subject to a real PyO3, exact-value, diagnostic, and
performance probe.

The fourth bounded Phase 0 spike is recorded in
[`i18n_research/compiler_linker/prototype-report.md`](i18n_research/compiler_linker/prototype-report.md).
It starts from ordinary authored Fluent and proves the tested compiler/linker
shape rather than another hand-generated fixture. Across two packages with

references through same-locale precedence, computed transitive typed inputs,
allowed repeated Slots while rejecting a reachable omission, and emitted
authored-to-generated source maps. Nineteen generated cases then matched across
the same Python, browser, and Rust runtimes. This makes the architecture viable,

The fifth bounded Phase 0 slice is recorded in
[`i18n_research/production_slice/prototype-report.md`](i18n_research/production_slice/prototype-report.md).
It moves the reduced compiler/linker subset into a real Rust cdylib and PyO3

### 4.4 Standards baseline

- Unicode CLDR/LDML is the data and identifier baseline for plural rules,
  number and date conventions, locale fallback data, calendars, and numbering
  systems: [Unicode TR35](https://www.unicode.org/reports/tr35/).
- Browser formatting is based on the ECMA-402 `Intl` family. It includes number,
  date/time, plural, relative-time, list, display-name, collation, and
  segmentation capabilities, but intentionally no general parsing API. Its
  locale data and exact localized output can vary between conforming
  implementations, so Citry defines semantic profiles and bounded fixtures
  rather than promising universal byte equality. See the
  [ECMA-402 API overview and implementation dependencies](https://tc39.es/ecma402/#sec-api-overview).
- Base direction belongs in `dir` markup. W3C recommends logical CSS properties
  and warns against using CSS alone to convey base direction. See
  [Structural markup and right-to-left text](https://www.w3.org/International/questions/qa-html-dir).

## 5. Requirements

### 5.1 Functional requirements

The first production-capable release must:

1. Configure the dormant built-in on one `Citry` engine and support concurrent
   render contexts without locale leakage.
2. Accept canonical selectable locale IDs, one application source locale, and
   package manifests with their own source locales. Allow an explicit graph of
   intermediate fallbacks, then use each message owner's source locale as its
   implicit final fallback.
3. Resolve locale and time zone at the request boundary, then allow a component
   subtree to override locale, direction, time zone, and named formats.
4. Resolve message IDs deterministically through application, library, and
   fallback catalog layers.
5. Support variables, plural and select logic, reusable private terms, related
   message attributes, and translator comments.
6. Derive and validate message IDs, variables, attributes, selectors, and rich
   placeholders from source ASTs. Read declared Python parameter types and
   translator descriptions from per-message `@param` comments, warn by default
   when a simple scalar parameter has no declaration, and require a concrete
   type wherever selectors, formatting, rich Slots, browser delivery, or a
   static call-site proof depend on it. Validate call sites and overrides
   without a duplicate author-written declaration map.
7. Format typed values on the server and browser through named profiles. At a
   minimum: decimal, percent, currency, date, time, datetime, relative time,
   list, and unit.
8. Write `lang` and `dir` on the real HTML element rendered by a subtree
   provider, let a framework adapter apply the same values when it owns the
   document shell, support explicit direction override, isolate interpolated
   unknown-direction text, and expose resolved direction to components.
9. Partition browser-required messages and format metadata. When dynamic
   in-page switching is enabled, load the target artifacts and switch locale
   atomically only after they are ready.
10. Preserve explicit `citry-ui` text props as the highest-precedence override.
11. Produce actionable development diagnostics without showing raw IDs in
    production accessibility names.
12. Integrate locale and catalog revision with only the caches whose output
    actually depends on them.
13. Encode every client-side message/formatter operand through a versioned,
    typed wire schema and reject values whose type or range cannot be preserved.
14. For dynamic switching, update each client provider's real wrapper element
    in the same atomic commit as visible and accessible content. Require complete
    selectable-locale coverage when a text-only or accessibility output cannot
    carry the selected message's actual language.
15. Preserve the locale and bundle selected by fallback resolution so catalog
    grammar, private terms, formatting, language markup, and bidi handling use
    the message's actual source rather than the request locale accidentally.
16. Treat a server-only subtree provider as a hard browser-ownership boundary,
    while allowing a nested client provider to start an independent boundary.

### 5.2 Non-functional requirements

- Source-locale rendering must not require a network request.
- Deterministic catalog compilation must produce byte-identical output for
  identical sources and tool versions.
- A package wheel must contain its authored descriptor, every declared source
  catalog, and every required generated-manifest artifact.
- Server and browser behavior must agree for the explicitly supported semantic
  profile matrix. Where ECMA-402 permits presentational variation, each profile
  declares an accepted fixture set or tolerance; unsupported profiles are
  server-only.
- Dynamic locale switching, when enabled, must not expose a mixed-language
  subtree between frames.
- Message formatting must remain escaped by default.
- Diagnostics must name the package, catalog, locale, message ID, attribute,
  and source span when known.
- Applications that leave the built-in extension unconfigured must load no
  catalogs and ship no i18n browser code. The prototype measures the remaining
  dormant Python import and engine-construction cost.

## 6. Proposed architecture and API

The public workflow is:

1. Configure package catalogs as import-package strings on the `Citry` engine.
2. Build an immutable locale context at the request boundary and pass it to
   `render(provides={"citry_i18n": context})`.
3. Author component source FTL in `messages` / `messages_file`, or app-wide
   source FTL in a standalone catalog package. Put Python input types in a
   comment attached to each message that accepts those inputs.
4. Call `self.i18n.tr()` and `self.i18n.format` in Python, or `tr()` and `fmt`
   in templates.
5. Use `<c-i18n tag="...">` when a subtree needs its own locale and real
   `lang` / `dir` element. Add `client` only when that subtree must switch in
   place.
6. Use the ordinary built-in `<c-trans>` with named `<c-fill>` content only when
   a translator must reposition application-owned markup.
7. Put browser-only dynamic message reachability in
   `Component.I18n.client_messages`.

### 6.1 Built-in extension and catalog ownership

The built-in `i18n` extension owns one immutable engine configuration and builds
immutable locale contexts on request. Applications configure it through the same
`extensions_defaults` mechanism as the other built-ins:

```python
from citry import Citry

app = Citry(
    extensions_defaults={
        "i18n": {
            # Default source for application-owned inline messages.
            "source_locale": "en-US",
            "locales": ("en-US", "cs-CZ", "ar-EG"),
            "catalogs": (
                "citry_ui_i18n",
                "my_app_i18n",
            ),
        }
    }
)
```

`catalogs` is an ordered sequence of Python import-package names, not one bare
string. Citry uses `importlib.resources` to load each package's authored
descriptor, locale files, and generated artifact manifest. Python imports that
resource package as part of the operation, so the initial contract uses a
dedicated top-level package with a side-effect-free `__init__.py`; it must not
import component modules. A nested resource package is insufficient because
Python executes each parent package's `__init__.py` first.
`"citry_ui_i18n"` therefore means "load the catalog resources from this
dedicated import package." One distribution may ship both `citry_ui` and
`citry_ui_i18n`. The resource name is separate from a distribution name such as
`citry-ui` and from the descriptor's stable owner ID. The list is ordered from
lowest to highest precedence, so `"my_app_i18n"` may override a `citry_ui`
message in the same locale.

Engine construction rejects a bare string in place of the sequence, a non-string
entry, an empty or relative name, a dotted segment that is not a Python
identifier, duplicate resource names, two descriptors claiming the same stable
owner, an unimportable package, a descriptor/manifest identity mismatch, a
missing or invalid descriptor, a missing production artifact manifest, and a
missing declared source catalog. Package CI owns the side-effect-free import
rule because Python cannot undo arbitrary import-time effects after detecting
them. A second
catalog-loading mode should add its own explicit configuration only when Citry
supports that mode; the one package loader does not need a wrapper object.

A catalog package may contain standalone app-wide or feature-wide source
messages that do not belong to a component, as well as translated locale
files. For example, `my_app_i18n` may own IDs such as `my-app-common-open` and
`my-app-common-close`. This is the supported v1 route for common messages
outside `Component.messages`; it uses the same manifest, ownership, checking,
and loading path rather than a second arbitrary-filesystem API. Component
sources and standalone package sources are separate source units in the same
in-memory project graph.

"Standalone package" means a dedicated Python import package, not necessarily
a separately published distribution or repository. An application distribution
may ship both `my_app` and `my_app_i18n` in one wheel. The i18n package has no
registration function or public Python classes. Its initial authoring layout is
conventional:

```text
my_app_i18n/
    __init__.py
    citry-i18n.toml
    locales/
        en-US/
            common.ftl
            navigation.ftl
        cs-CZ/
            common.ftl
            navigation.ftl
    _compiled/
        manifest.json
        link.json
        server.json
```

That is the exact current v1 layout. Browser partitions are not written yet.
When browser switching ships, its generated files will be added under a
versioned layout documented at that time.

`__init__.py` is empty and side-effect-free. `citry-i18n.toml` is the small
authored package descriptor:

```toml
schema_version = 1
owner = "my-app"
source_locale = "en-US"
```

V1 does not require a Python API, an entry point, a Citry-specific
`pyproject.toml` field, a configurable resource directory, or a hand-maintained
list of every FTL file. Citry discovers only
`locales/<canonical-locale>/**/*.ftl` under the configured import package,
sorts normalized relative paths deterministically, and treats each FTL file as
one source unit. A missing source-locale directory, a noncanonical locale
directory, two canonically equivalent directories, or a source file outside
that fixed tree is an error. A future second loading mode must use distinct
configuration rather than changing what an import-package string means.

`locales` is the allowed set for request and subtree selection. Citry
canonicalizes every entry and rejects an empty sequence, an unordered
collection, or two spellings that become the same locale. `default_locale`
defaults to `source_locale` and must be in `locales`. `source_locale` itself may
be outside `locales`: that is useful when the authored source language must stay
as the final fallback but users are not allowed to select it directly.

`citry ext run i18n compile` currently generates `_compiled/manifest.json`,
`_compiled/link.json`, and `_compiled/server.json`. Generated files are not an
authoring API. The package manifest records the discovered source paths and
hashes plus both artifact hashes. The link artifact carries checked messages,
attributes, parameter interfaces, private terms, unresolved public references,
source ranges, compiler/schema versions, and revisions. The server artifact is
the final package-only result. Browser partitions remain open.

The compiler reads `citry-i18n.toml` and raw sources before an artifact manifest
exists, so creating a new package has no generated-file bootstrap problem. A
development engine may build and refresh the same artifacts in memory for hot
reload. A production build and production engine require all three generated
files. The engine checks their hashes, validates the link-unit schema, compiler
version, semantic revision, package owner, source digests, and message/term
identities, and rebuilds the package-only result from `link.json`. That result
must match `server.json`. Replacing one generated file and merely updating its
hash is therefore still rejected.

`server.json` is not used as linker input. It has already chosen package-only
winners and rewritten public references, so concatenating final server files
would give the wrong result after an application override. `link.json` keeps
those choices unresolved. The project linker assigns the configured layer and
precedence, combines multiple package link units with application component
messages, then makes locale-major and fallback decisions for the complete
project. Tests prove that this path performs zero package FTL parses and still
allows an application source-locale override while choosing a package
translation for another locale.

The distribution's normal Python build backend must include the descriptor and
generated artifacts as package data in the production wheel. It may also ship
FTL for inspection, but production linking does not read or require it. Source
distributions and editable development installs keep FTL for compilation and
hot reload. This is not
locale discovery metadata: it is the same backend-specific inclusion mechanism
already used for JavaScript, type markers, templates, or other non-`.py` files.
Citry documents recipes for supported build backends, while package CI builds
the wheel and verifies the descriptor and generated paths named by the
manifest. An installed package with an omitted descriptor or required artifact
fails package verification and engine construction rather than silently losing
translations.

The important contracts are:

- built-in availability with explicit configuration;
- immutable selectable-locale, owner, source-locale, and catalog topology after
  engine construction;
- one explicit locale, direction, and time zone value for each render tree;
- deterministic layer order, specified from lowest to highest precedence;
- no catalog parsing, locale data load, or browser dependency when unconfigured.

Each generated package manifest declares its source locale, stable IDs, locale
resources, and revision. Each configured package contributes one lookup layer.

Source locale belongs to the package that defines a message, not universally
to the engine. The engine's `source_locale` is the default for application-owned
inline messages; a packaged manifest is authoritative for its own IDs. This
allows, for example, a Czech-authored application to use `citry_ui`, whose
source catalog is English. Each stable ID has exactly one defining owner.
Application translation/override layers do not acquire ownership merely by
supplying that ID. If the application also has a packaged manifest, its source
locale must agree with the engine default or construction fails; an engine
cannot reinterpret an existing package's source text.

The application layer has higher lookup precedence than a library layer within
the same locale. Lookup is locale-major so an active-locale library translation
beats an application override that exists only in a fallback locale:

```python
def resolve(message_id, attribute, context, topology, layers_low_to_high):
    owner = topology.owner(message_id)
    locales = dedupe((
        context.locale,
        *context.fallback_locales,
        owner.source_locale,
    ))
    for locale in locales:
        bundle = topology.linked_bundle(locale)
        for layer in reversed(layers_low_to_high):
            pattern = bundle.lookup(layer, message_id, attribute)
            if pattern is not MISSING and topology.refs_resolve_at(
                pattern, locale, layers_low_to_high
            ):
                return ResolvedMessage(
                    pattern=pattern,
                    locale=locale,
                    direction=topology.direction(locale),
                    bundle=bundle,
                    owner=owner,
                )
    raise MissingSourceMessage(message_id, attribute)
```

Each requested value or attribute follows this traversal independently.
Resolution returns the selected pattern together with its catalog locale,
direction, owner, and bundle, not a bare string. Translator-authored plural,
number, date, term, and private-reference evaluation uses that selected locale
and bundle. For example, an English source fallback selected inside an Arabic
request uses English plural rules and the English bundle's private terms.
Private terms use the selected bundle. A public message reference inside the
pattern resolves through normal layer precedence at that same selected locale,
without taking its own fallback path. A candidate pattern is renderable only if
all transitive public references resolve at that locale; otherwise the outer
resolver continues to its next locale. Reference cycles are build errors. This
single-locale invariant prevents one text projection from silently combining
language runs that would need separate semantic markup. Direct `fmt` calls
still use the active `LocaleContext`, because they are formatting application
values rather than evaluating a selected catalog pattern.

Fluent public references share the outer message's argument map. Citry
therefore computes an effective typed interface for each message value and
attribute, not only the variables directly present in that pattern. The
effective interface is the deterministic transitive union of its direct typed
variables and the effective interfaces of same-locale public references
selected by the defining-owner source graph. A wrapper such as
`wrapper = { target }` automatically requires `$x` when `target` requires
`$x`; the wrapper does not repeat an `@param` merely to expose that inherited
input. If direct and transitive paths, or two referenced messages, give the
same variable different canonical Python types, compilation fails at both
declarations. The closure is computed per value or attribute, detects cycles,
and carries required `Slot` presence and repeatability rules as well as scalar
types. Overrides and translations may consume a subset of scalar inputs but may
not add an argument or omit a required `Slot` from a reachable path. This
conservative source interface remains stable even when the selected override
happens not to use every argument.

Fluent does not implement the source-unit boundary described here. Its runtime
combines one or more FTL resources into a locale bundle, and message and term
identifiers share that bundle's namespace. Adding a resource with an existing
identifier reports an override conflict unless the caller explicitly chooses
the overriding API. A Fluent term is private only in the sense that application
code cannot retrieve it directly; it is not private to one FTL file. See the
official [terms guide](https://projectfluent.org/fluent/guide/terms.html) and
[`FluentBundle::add_resource`](https://docs.rs/fluent-bundle/latest/fluent_bundle/bundle/struct.FluentBundle.html#method.add_resource).

Source-unit-local terms are a Citry compiler rule. A source unit is one inline
`Component.messages` block, one `messages_file`, or one standalone FTL file.
The three evaluated Fluent APIs cannot implement Citry's public-reference and
private-term scopes by simply formatting one bundle per source layer. A
layer-local bundle cannot see a higher-precedence public reference, while
naively merging raw resources makes duplicate public IDs and same-named private
terms collide. Citry therefore links an intermediate catalog graph after the
engine topology is known. Every definition receives a deterministic,
Fluent-safe internal ID derived from its owner, layer, locale, source unit, and
stable source ID. A private-term reference is rewritten to the internal term
in the definition's own source unit and layer. A public-message reference is
rewritten to the internal definition selected by normal same-locale precedence.
The referenced definition's own rewritten private terms remain in its defining
source unit and layer. The linked artifact retains source maps, detects cycles,
and is revisioned with the topology. Its internal IDs are not public catalog
IDs or API inputs.

The runtime spike first established that all three candidates can render one
illustrative, already-generated linked artifact. The follow-up compiler/linker
spike then exercised actual package and application precedence, per-owner
fallback, independent attributes, transitive typed interfaces, repeated Slots,
deterministic internal IDs, and authored-to-generated source maps. That bounded
result proves the proposed linking rules are implementable for the tested
subset. It does not yet prove the production Rust/PyO3 linker, the complete
accepted Fluent subset, production diagnostic objects, browser artifact
loading, or incremental relinking.

Within one layer and locale, duplicate IDs are errors. An override across
layers may use any subset of the source variables but cannot introduce a
variable absent from the defining source interface. A translation may omit an
attribute; independent per-attribute lookup must still resolve every attribute
required by a call site or component. Translators may change selectors and
locale-specific categories. Rich-placeholder names and required presence
remain structural because they protect application-owned nodes;
repeated uses are valid and expand independently. An application
that wants one literal to win across all locales uses an explicit component
prop or supplies the override in each relevant locale.

The defining owner's source locale is always the implicit final message
fallback, so there is no required `fallback_locale` argument that repeats it.
An optional `default_locale` chooses the active locale when no explicit context
exists and defaults to the application's source locale. An optional `fallbacks`
map adds intermediate parents or aliases before the owner source is appended at
lookup. `locales` controls request/subtree choices; package source
locales may be fallback-only. Engine construction canonicalizes every node and
rejects duplicate canonical locale IDs, unknown fallback nodes, cycles,
duplicate defining owners, a missing owner source catalog, or an owner source
that cannot resolve every required source value and attribute. The catalog
revision hashes this complete owner/source/layer topology as well as catalog
content, so a context identity cannot silently reuse an older ownership graph.

### 6.2 Locale context and precedence

The locale context is an immutable value:

```python
@dataclass(frozen=True)
class LocaleContext:
    locale: str
    # Shared intermediate chain; a message owner's source is appended at lookup.
    fallback_locales: tuple[str, ...]
    direction: Literal["ltr", "rtl"]
    time_zone: str | None
    tzdb_revision: str
    catalog_revision: str
    formats_revision: str
```

Components resolve it in this order:

1. nearest `<c-i18n>` subtree override;
2. the `citry_i18n` value passed to the root `render(provides=...)` call;
3. engine defaults.

The engine owns immutable configuration and compiled catalog caches. It does
not own a mutable current locale. The provided value under `citry_i18n` is the
single source of truth for one component tree. Two requests can render with
different values at the same time because each value travels on its own render
path.

The root flow is:

```python
i18n = app.extensions.get_extension("i18n")
context = i18n.make_context(
    locale="cs-CZ",
    time_zone="Europe/Prague",
)

rendered = Page().render(
    provides={"citry_i18n": context},
)
```

`make_context()` validates the locale and time zone and returns data; it does not
change engine or task state. `render()` copies the provided mapping into the
root render. `self.i18n.context`, `tr()`, `fmt`, and `<c-trans>` all read that
same `citry_i18n` value. `<c-i18n>` uses `Component.provide()` to replace the
value for its descendants. When no value was passed or provided, components use
the engine's fixed default context.

A direct render inside `template_data()` is a separate root. It does not take
the caller's locale implicitly:

```python
def template_data(self, kwargs, slots):
    context = self.i18n.context
    summary = AccountSummary().render(
        provides={"citry_i18n": context},
    )
    return {"summary": summary}
```

The caller must pass the context again. This keeps locale selection predictable:
another page, task, test, or thread cannot change the nested component's locale
merely through its own provided context. Applications may pass a context as a
Kwarg and call `provide()` on a component when they want that dependency in the
component's Python signature. The root mapping is the shorter request-entry form
and keeps ordinary component Kwargs clear.

Code outside a component render also stays explicit. Pass `context=` to
`i18n.tr()` or `i18n.resolve()`, and call `i18n.format_for(context)` before an
imperative formatting operation.

Web adapters may supply resolvers for a route segment, authenticated profile,
session, cookie, or `Accept-Language`. Core negotiation receives ordered
candidates and matches only the configured selectable set. It does not prescribe
which HTTP source wins. Unknown explicit application locales are errors;
unsupported negotiation candidates fall through to the configured default
locale. Message lookup then appends the defining owner's source locale.

A locale never selects a time zone implicitly. `en-US` users can live anywhere,
and countries can span several zones.

### 6.3 Subtree provider

The public Python class is `I18nProvider`, registered under the reserved
built-in tag `<c-i18n>`. The `C` class prefix remains owned by `citry-ui` and is
not used by a Citry built-in. The provider writes the resolved server context
through `Component.provide()`. Its `tag` input decides whether it also renders a
real HTML element:

```html
<c-i18n c-context="arabic_context" tag="section">
  <c-AccountSummary />
</c-i18n>
```

This renders a `<section lang="ar-EG" dir="rtl">` around the slot. The provider
derives direction unless the author supplies an explicit `direction`. Authors
choose the tag so the wrapper is valid in its HTML context. For example, a
provider directly under `<table>` can use `tag="tbody"` instead of inserting a
`div`. Citry validates the tag as an ordinary HTML tag, rejects component names
and unsafe names, owns the wrapper's `lang` and `dir` attributes, and rejects a
conflicting author value for either attribute.

The `context` input accepts the immutable value passed into the component tree.
It is the explicit base for this boundary. Optional `locale`, `direction`, and
`time_zone` inputs can derive a child context from that base for a nested
override. When `context` is omitted, the provider inherits the nearest outer
provider or uses the engine's fixed default.

When `tag` is omitted, the provider changes only the server render context and
emits no wrapper. That form supports rootless and multi-root slots, but it cannot
own in-page locale switching because there is no element whose `lang` and `dir`
the browser can update. Core therefore requires `tag` when `client=True`.

Provider data follows Citry component ownership through slots, morphs,
retained DOM, and teleports. A physical portal target does not silently change
its logical locale owner.

Citry can render a component fragment, so core cannot assume that every render
contains the page's `<html>` element. If Citry renders the whole document, the
application makes ownership explicit:

```html
<c-i18n tag="html" client>
  <head>...</head>
  <body>...</body>
</c-i18n>
```

If another framework renders `<html>`, its Citry adapter reads
`i18n.context.locale` and `i18n.context.direction` from the Python extension and
writes those values to that framework's document shell. Core does not search
for or mutate an unrelated `<html>` node after rendering.

One public `client: bool = False` input controls browser participation. Server
provision always happens because the initial HTML must use the same context as
any browser continuation. A provider with `client=False` emits no i18n browser
data or dependency when no client provider owns its ancestor. If it is nested
inside a client provider, it creates a hard behavioral boundary: switching the
outer provider does not update its subtree. The browser needs a real element
for that ambient `unprovide` boundary because the current client graph does not
serialize Python provide/inject records. The nested false provider therefore
requires `tag`; omitting it fails the production check. Citry owns the wrapper
and its private core ambient instruction. The already-loaded outer runtime
handles it, so the false provider adds no i18n runtime or catalog dependency.
A browser-switchable message below that boundary is an error unless a nearer
provider sets `client=True`; that nearer provider then switches independently.

With `client=True`, the provider serializes one strict-JSON locale record plus
its provider policy and installs one stable client service:

```js
$component(({ data, provide }) => {
  const i18n = createI18nService(data);
  provide("citry_i18n", i18n);
});
```

The provided service exposes readonly `context` and `status`, an asynchronous
`switchLocale(locale)` operation with success/failure, and validated `tr()` and
`fmt` operations limited to the boundary's loaded manifest. That manifest
contains literal IDs/profiles extracted from client-owned template operations
plus dynamic IDs declared by `Component.I18n.client_messages`.
`resolveMessage()` returns immutable selected-locale metadata, while
`bindMessage()` associates that result with a declared DOM sink. Text-only
imperative `tr()` is permitted only where the manifest proves
equivalent-language coverage for every selectable locale; switchable component
labels use the binding API. Direct mutation is not an API. The build emits a
canonical selectable-ID table and accepted-alias map with the shared Rust
canonicalizer's data and schema revision. `switchLocale()` maps and validates the target only
through that artifact; it does not rely on the browser's ambient ICU/CLDR data.
It then loads and validates artifacts, supersedes stale generations, and
commits or rejects as one transaction. Components may subscribe to the
readonly context or status; failures leave the prior context intact.

The actual implementation defines a typed `JsData` schema and serializes only
locale IDs, the canonical-ID/accepted-alias map, intermediate fallback IDs,
direction, time-zone ID, public revisions, and a strict provider-policy record.
That policy distinguishes
unset/inherited fields, explicit values, explicit clears, and named-format
overrides. It never serializes formatter objects, whole catalog contents,
request objects, or secrets. Nested providers recompute outermost to innermost
on a switch: inherited fields follow the new parent, while explicit child
values remain fixed. The entire nested result validates before any boundary
commits.

The flag is known before descendants render. To preserve zero i18n browser cost
when false under Citry's class-level JS dependency model, the provider renders
a private browser-service child only in the true branch. That child owns
`js_data()` and the `$component` registration; it is an implementation detail,
not a second public provider API. A false branch outside a client boundary owns
no switchable nodes and requests no i18n asset. A false branch below a client
boundary renders the required real wrapper and uses the core ambient
`unprovide` operation supplied by the already-loaded browser runtime.

The provider's hook-level `provide()` owns the whole logical component, so it
works for rootless and multi-root output and keeps logical ownership through
slots and teleports. A message or formatter node that requests in-page
switching outside `<c-i18n client tag="...">` fails the production check; it does not
silently add browser behavior to an ancestor server-only provider.

The wrapper rendered by `<c-i18n client tag="...">` is the browser update
target. On a successful switch, Citry stages its new `lang` and `dir` together
with the boundary's text and accessibility changes, then commits them in one
operation. No special template attribute is needed to register that element.

A text-only `tr()` result cannot attach a different `lang` to itself. Static
checking therefore requires every selectable locale for a client-switched or
accessibility output to resolve to an equivalent language tag. Server code that
deliberately permits a source-language fallback uses
`self.i18n.resolve(...)`, receives
`LocalizedText(text, locale, direction, used_fallback)`, and
applies its ordinary `lang` and `dir` fields to an application-owned element.
Whole-message bidi isolation still protects ordering, but it does not replace
correct language markup.

For a JavaScript-owned text or attribute sink, a typed `ClientMessageRef`
carries a stable Citry ownership and target ID. Component metadata associates
that ID with one DOM target, and client code registers it through
`bindMessage(ref, element, target)`. A switch updates the target in the same
transaction as the provider wrapper. The production check rejects an unbound
reference and rejects a sink whose selectable catalogs would require a
different per-message language tag. This is the contract Pagination and
Combobox use instead of reapplying stale label strings.

Provider inheritance is per field and uses an internal unset sentinel so
"inherit" differs from an explicit `None` where clearing is supported:

- an omitted locale inherits the parent; an explicit locale is canonicalized,
  checked against the selectable set, and receives its precomputed intermediate
  fallback chain;
- an explicit direction wins; if locale changes and direction is omitted,
  direction is derived from the new locale; if both are omitted, direction is
  inherited;
- an omitted time zone inherits; an explicit `None` clears an inherited zone
  only on APIs that deliberately allow zone-free formatting;
- named format overrides merge by profile name, while each profile record is
  replaced as one typed value rather than deep-merged option by option;
- selectable locales, catalog layers, defining owners and source locales, and
  compiler versions are engine topology and cannot change in a subtree.

Reserved template-name checks include slot/fill data names, loop variables,
local bindings, component `TemplateData`, render globals, and extension
facades.

### 6.4 Component catalog declarations

Messages use a fourth primary inline/file asset pair. The source locale may be
inline with its component:

```python
from citry import Component

class AccountCard(Component):
    citry = app

    class Kwargs:
        name: str

    class I18n:
        # Only IDs selected dynamically by browser code need listing.
        client_messages = ("my-app-account-card-actions",)

    template = """
    {{ tr("my-app-account-card-greeting", name=name) }}
    """

    messages = """
    # Greeting shown above an account summary.
    # @param {str} $name - User name shown in the greeting.
    my-app-account-card-greeting = Welcome, { $name }.

    # Label and accessible name for the actions menu.
    # @param {str} $name - User name whose actions are shown.
    my-app-account-card-actions = Actions
        .aria-label = Actions for { $name }
    """
```

`messages` and `messages_file` are mutually exclusive and inherit, resolve,
load, watch, and invalidate like `template` / `template_file`. `get_messages()`
returns the loaded source. Only the defining package's source locale may live
inline with Python; translator-owned locales remain external files so
translation workflows do not edit product source.

The Fluent AST supplies message IDs, attributes, referenced variable names,
message and term references, selectors, variants, function calls and options,
and terms. Citry's positioned `Slice` adapter supplies exact source spans
without changing the upstream AST. Authors do not repeat those facts in a
separate mapping. A source comment supplies the one fact FTL does not carry:
the Python type of each input. Its initial syntax is:

```text
# @param {PythonType} $variable - Optional translator-facing description.
```

One or more consecutive `#` comment lines immediately above a message are that
message's comment in Fluent. Citry reads `@param` lines only from that attached
comment. Citry gives the message value and all of its attributes one declared
argument namespace, while deriving the required subset separately for each
output. Fluent does not attach a comment to an individual attribute. A normal
top-level `#` comment between a message value and an attribute ends the message,
so the following indented attribute is no longer attached to it. An indented
`# @param` line is text in the message pattern, not a comment. Put every
attribute parameter on the one message comment above the message. The official Fluent
[comments](https://projectfluent.org/fluent/guide/comments.html),
[variables](https://projectfluent.org/fluent/guide/variables.html), and
[attributes](https://projectfluent.org/fluent/guide/attributes.html) guides use
the same message boundary.

The scope is per message. It is not per variable spelling across a component,
file, or package. These two `$name` inputs are independent and may have
different types:

```text
# @param {str} $name - User name.
my-app-account-greeting = Welcome, { $name }.

# @param {int} $name - Numeric account code.
my-app-account-code = Account { $name }.
```

Within one message, repeated `$name` uses in the value and any attributes have
one type. Put the declaration on the message comment even when only an
attribute uses it:

```text
# @param {str} $name - User whose actions are available.
my-app-account-actions = Actions
    .aria-label = Actions for { $name }
```

Annotations are written only in the defining source catalog. Translations
inherit them and may not redefine them. Citry parses the type name rather than
executing it. The current compiler accepts a closed, language-neutral list:
`str`, `int`, `Decimal`, `datetime`, and `Slot`. It does not inspect imports in
the component's Python file, evaluate a Python type expression, or accept a
dotted import path. `Slot` marks an application-owned rich placeholder. Types such as
`date`, `time`, formatter-specific values, and containers such as `list[str]`
remain future work. They must not be documented as accepted until the compiler,
runtime wire format, checker, and browser runtime all support them.

A resource-wide `### @param` default could reduce repetition, but it would also
make a common name such as `$name`, `$value`, or `$count` acquire hidden meaning
from its file location. Moving a message between files could change its
contract; independently composed component blocks could disagree; and one
description would rarely fit every use. V1 therefore supports per-message
declarations only. If real catalogs later show unacceptable repetition, a
resource-wide form may be added as an explicitly source-unit-scoped default,
with a message declaration taking precedence. It must never create a
component-wide, package-wide, or project-wide variable namespace. An explicit
reusable named schema is another future option and is less dependent on file
layout.

Variables required only through a public message reference inherit their type
from the referenced defining-source interface. Redeclaring them on the wrapper
is an unused annotation unless the wrapper also uses the variable directly.
This is reference dependency, not global variable scope. If two paths from one
message require the same argument name with incompatible concrete types,
compilation fails at both declarations. Unrelated messages remain independent.

Missing `@param` metadata is a configurable code-smell diagnostic named
`citry.i18n.missing-param-type`. The application setting and matching
per-component `Component.Lint` override are:

```python
from citry import Citry, Component, LintSettings

app = Citry(
    lint=LintSettings(rule_i18n_missing_param_type="warning"),
)

class LegacyCopy(Component):
    class Lint:
        rule_i18n_missing_param_type = "ignore"  # or "warning" / "error"
```

The default is `"warning"`. A simple server-only scalar interpolation without
an annotation is recorded with an unknown static type and checked against the
runtime's safe scalar set. `"ignore"` suppresses the diagnostic, while
`"error"` makes it fail checking. A concrete declaration remains mandatory,
regardless of lint severity, for a `Slot`, selector, number/date formatter,
client wire operand, or any other operation whose correctness requires a known
type. Malformed, duplicate, unused, or unsupported annotations and incompatible
concrete types are semantic errors, not suppressible lint warnings. The
description is optional translator metadata and does not affect compatibility.

This design therefore:

- derives IDs, attributes, variables, and selector structure from FTL;
- attaches parsed Python parameter types and descriptions to that structure,
  then computes the per-output transitive interface through public references;
- cross-checks literal Python and template calls against the resulting typed
  interface;
- infers number/date intent where Fluent built-ins make it explicit;
- uses `Component.I18n.client_messages` only for browser reachability that
  static template analysis cannot infer; listing one ID includes all its
  attributes;
- requires every browser-executed operand type to be inferred from typed kwargs,
  `@param` metadata, literals, or formatter calls; a client operation whose type
  cannot be proven encodable fails the production check.

`I18n` is the normal nested configuration class owned by the built-in extension.
Its initial component field is `client_messages`. The value is a tuple of
non-empty message IDs; duplicates and IDs absent from the complete project
catalog graph are errors. The IDs may be defined by this component, another
component, or a configured standalone catalog package. Normal extension-config
inheritance applies, so the nearest declaration wins as one immutable tuple.
Literal client-owned `tr()` calls are inferred and do not need to be repeated
there.

The extension fixes its public component-config name as `I18n`. Engine-only
fields such as `catalogs`, `source_locale`, and `locales` are invalid
inside that class, while `client_messages` is invalid in engine defaults. The
normal Citry extension-config rules cover C3 inheritance and `I18n = None`; the
checker additionally rejects inherited client behavior whose required ID was
removed by a nearer replacement tuple.

Browser reachability does not live in FTL comments because it is a component
delivery setting, not part of a message's interface. `@param` is machine-readable
only in the defining source and is stored in the manifest; ordinary source and
translation comments remain translator guidance. The explicit
`Component.I18n.client_messages` tuple and statically recognized calls keep
browser delivery in application code.

Catalogs are packaged and compiled by feature or module, not instantiated as
one runtime bundle per component. Component declarations contribute sources,
defining-owner/source-locale metadata, and browser reachability to a package
manifest. Runtime loaders assemble a small number of deterministic layers per
locale.

An unconfigured engine may still load a component class containing the message
asset, but calling `tr()` raises a pointed configuration error. For `citry-ui`,
the English FTL is the single authoring source. Its package build generates a
checked Python constants/default-metadata module from that FTL; component
Kwargs defaults import those generated values. CI regenerates and compares the
module byte-for-byte, preventing the dormant English fallback and catalog from
drifting while preserving current typed defaults and documentation.

ID conventions:

- newly defined exported IDs start with an owner/package prefix followed by a
  component or feature prefix, such as `my-app-account-card-greeting` or
  `citry-ui-pagination-next-page`; this BEM-like hierarchy is a traceability and
  collision-avoidance convention, not a derivation from English text;
- a deliberate application override in a higher-precedence layer uses the
  existing target ID, so the new-ID prefix rule does not block overriding a
  library message;
- source IDs are stable API, not generated from English text;
- attributes group outputs belonging to one widget, such as `.label`,
  `.aria-label`, `.title`, and `.description`;
- `$variable` names are local to one message contract. Reusing `$name` in
  unrelated messages or components is valid and needs no prefix;
- Fluent `-term` names are private to their defining source unit in Citry's
  catalog graph. The compiler assigns them internal owner/source identities,
  so two components may both define `-brand` without a collision. Another
  source unit cannot import that private term. Cross-source reuse uses a public
  namespaced message ID; a standalone common message may use private terms from
  its own FTL file internally. Current Fluent term parameters are literals, so
  variable-valued named term arguments and `Slot` forwarding through terms are
  source errors;
- variable names, `@param` Python types, and their use in selectors or explicit
  formatters are part of the extracted contract; statically known call sites
  are checked at build time and dynamic Python calls validate at runtime;
- translator comments explain UI position, constraints, and variable meaning.

Within one locale and layer, two source units defining the same public message
ID are an error; file order never chooses the winner. The project index keeps
the source unit and span for every ID, so the error points to both components.
The generated runtime artifact may combine many source units for efficiency,
but that does not erase their ownership or make a hand-maintained giant FTL
file the source of truth.

### 6.5 Message APIs

The built-in extension config is attached as `self.i18n` before cache lookup.
Python uses it directly, with no imported `use_i18n` helper:

```python
greeting = self.i18n.tr(
    "my-app-account-card-greeting",
    name=account.name,
)
actions_label = self.i18n.tr(
    "my-app-account-card-actions",
    attr="aria-label",
    name=account.name,
)
balance = self.i18n.format.currency(
    account.balance,
    "EUR",
    format="account-balance",
)
```

The extension adds two request-bound template globals. `tr(...)` is the template
form of `self.i18n.tr(...)`. `fmt` is the template form of
`self.i18n.format`. A plain message visibly produces text and goes through
normal template escaping:

```html
<p>{{ tr("my-app-result-count", count=result_count) }}</p>
```

There is no separate `i18n` template global because it would duplicate those
two facades. Components that need locale metadata use `self.i18n.context` in
Python or `<c-i18n>` in the template. When i18n is configured, `tr` and `fmt`
are reserved template names.
Engine/render globals, component `TemplateData`, or another extension claiming
one of them fail at the earliest deterministic definition/configuration point.
`inspect_template_namespace()` reports their owner and type so linting and
runtime precedence cannot disagree.

The V3 AST should recognize literal `tr()` calls as an i18n operation rather
than treating them as an opaque arbitrary function. That gives extraction,
linting, source spans, and optional client ownership the information they need.
If the best implementation requires a Rust parser or AST change, that is part
of the design. A dynamic template ID is browser-executable only as the typed ID
operand described below and only when every possible value is listed in
`Component.I18n.client_messages`.

Browser-executable template operations use a closed AST subset. The whole
escaped interpolation or whole attribute value must be one direct built-in
`tr(...)` or `fmt.kind(...)` call with operands that the typed wire can capture.
A message ID is either literal or one captured `ClientMessageId` enum operand
whose finite values exactly match an allowed subset of
`Component.I18n.client_messages`; a
named format profile remains literal in the initial contract. The server and
client reject an enum value outside that manifest before lookup. At compile
time Citry expands every legal enum member at that call site. Every member must
define the requested literal attribute, accept every supplied variable name
with a compatible type, and have every source-required variable satisfied by
the call. A heterogeneous set instead uses separate call sites or a
discriminated per-ID reference whose schema carries its own operands; a plain
enum cannot erase incompatible message interfaces. `<c-trans>` calls are their
own recognized form. A call inside concatenation, a conditional, `.upper()`,
another helper call, or any other Python expression is not client-executable
merely because the AST found the inner call. Such composition remains ordinary
SSR output outside a client boundary. Inside `<c-i18n client tag="...">`, it fails the
production check rather than becoming stale after a switch. Phase 0 may
deliberately add individually specified pure operations, but it may not treat
arbitrary Python as browser replay metadata.

The selected message runtime must not format around Citry. Fluent
`NUMBER`/`DATETIME` calls and plural/ordinal selection delegate to Citry's
normalized formatter and plural service, regardless of whether the selected
server backend is Babel, PyICU, or another implementation. Application source
uses ordinary Fluent numeric selectors. The typed catalog compiler rewrites
those selector heads as an internal `CITRY_PLURAL` call and rewrites exact
numeric variant keys to collision-free internal keys, so translators keep the
standard Fluent authoring shape while the runtime cannot bypass Citry's plural
service. Exact values are compiler-owned function metadata, not an option a
translator writes. An authored ordinal numeric selector uses the Project
Fluent guide's `NUMBER($value, type: "ordinal") ->` form, which Citry
recognizes and compiles before any candidate runtime sees it. The pinned Python,
browser, and Rust runtimes do not agree on direct `type: "ordinal"` semantics.
The compiler therefore consumes that compiler-owned `type`, generates
`CITRY_PLURAL(..., mode: "ordinal")`, and keeps display formatting in the named
`NUMBER` profile inside variants. Exact
matching uses the compiler-owned variant key, including when the operand is
signed negative zero; it never derives the internal key from the runtime
operand's spelling. The generated artifact retains a source map to the authored
selector, mode, and variants. A string selector is left unchanged.
Direct display of a typed number or date without `NUMBER` or `DATETIME` is a
source error because there is no safe implicit named profile. Developer-owned
typed wrappers carry named profiles and semantic inputs such as currency,
calendar, numbering system, and time zone. Phase 0 defines a small
translator-overridable presentation-option allowlist; unsupported or
cross-runtime-incompatible options fail catalog compilation.

`tr()` always returns text. Internally it projects a `ResolvedMessage` carrying
the selected catalog locale, direction, owner, and bundle. Python also exposes
`self.i18n.resolve(...)` for a caller that needs an immutable `LocalizedText`
record with `text`, `locale`, `direction`, and `used_fallback` fields so an
existing application-owned element can apply the actual message `lang` and
`dir`. This is a metadata-bearing variant of the same lookup, not a component
and not an imported `use_i18n` facade.

The public authoring form remains ordinary `{ $value }`. Before a Fluent
runtime sees it, the typed catalog compiler wraps every displayed scalar
boundary in the internal `CITRY_TEXT($value)` operation and source-maps that
wrapper to the original placeable. `CITRY_TEXT`, `NUMBER`, and `DATETIME`
return Citry-owned First Strong Isolate / Pop Directional Isolate pairs.
Selectors do not receive display isolation. Runtime-owned Fluent isolation is
disabled so Python, Rust, and browser behavior cannot drift. Custom functions
are forbidden unless their typed output and isolation behavior are part of the
same compiler allowlist.

Catalog validation parses Fluent first, then traverses every decoded text and
string literal in every value, attribute, term, selector branch, and function
option. It rejects Unicode `Bidi_Control` whether authored literally or through
Fluent `\u` / `\U` escapes. A raw-source scan is only defense in depth because
escapes can hide the decoded code point. The compiler also validates the output
contract of every allowlisted function; only its own balanced isolation
operations may introduce controls.

Untrusted scalar placeables reject both `Bidi_Control` and every Unicode
bidirectional paragraph boundary (Bidi_Class `B`, including CR, LF, NEL, the
information separators, and U+2029). One FSI/PDI pair cannot safely cross a
paragraph boundary. Multiline application content needs separate structural
markup rather than an inline scalar escape hatch. Compiler-owned isolate
controls exist only in generated operation results, never in authored FTL. A
later trusted-control escape hatch would need an explicit type and security
review; ordinary strings cannot opt out. Where markup exists, an application
may instead establish a structural `<bdi>` or explicit `dir` boundary.

Unknown-direction interpolated values are therefore isolated during message
formatting. The whole resolved message has a known direction, so when it
differs from the provided context the text projection wraps each bidi paragraph
independently with Left-to-Right Isolate or Right-to-Left Isolate, according to
`ResolvedMessage.direction`, followed by Pop Directional Isolate. CRLF is one
preserved paragraph separator. It never infers the known message direction from
its first character or lets one isolate pair cross a paragraph boundary.
These controls follow the isolate model in
[Unicode Bidirectional Algorithm UAX #9](https://www.unicode.org/reports/tr9/).

Isolation protects ordering, but it does not declare the spoken language. A
plain `tr()` call has no element of its own on which to put `lang`. `check`
therefore requires an equivalent-tag translation for every selectable locale
when the call is client-switched, produces an accessible name or description,
or otherwise cannot carry language metadata. Exact tag inequality is the safe
default, including script or region changes; an application may configure a
markup-equivalence class only when it proves the variants share language,
resolved script, and direction. Server code that permits cross-language
fallback calls `self.i18n.resolve(...)` and applies the returned locale and
direction to an ordinary application-owned element. Development may render a
directionally isolated source fallback with a structured diagnostic so missing
work remains inspectable.
The comparison uses canonical BCP 47 tags and follows W3C's
[language-tag guidance](https://www.w3.org/International/articles/language-tags/),
not primary-language string comparison.

Rich localization is a separate structured operation because some languages
need to reposition an application-owned link, emphasis node, icon, or other
inline element. For example, English may say "I accept the [Terms]" while
another locale puts the linked phrase first. The source message declares the
placeholder as a typed application-owned slot:

```text
# @param {str} $account_name - User accepting the terms.
# @param {Slot} $terms_link - Link to the application's terms page.
my-app-terms-acceptance = { $account_name } accepts the { $terms_link }.
```

The preferred API is an ordinary built-in Python component with an existing
named fill:

```html
<c-trans
  message="my-app-terms-acceptance"
  c-values="{'account_name': account.name}"
>
  <c-fill name="terms_link">
    <a href="/terms">{{ tr("my-app-terms-name") }}</a>
  </c-fill>
</c-trans>
```

`tr()` still always returns text. `<c-trans>` exists only for the different
result type: a constrained inline fragment containing translated text plus
application-owned nodes. It cannot choose an arbitrary component or emit
translator-authored HTML.

The input is named `message`, not `id`. On an HTML-shaped tag, `id` looks like
the native element identity attribute; `message` says directly that the value is
the Fluent message key.

The `values` input is one mapping for all non-`Slot` message parameters. That
keeps message names from colliding with component inputs such as `message`. Static
mapping keys are checked against the source `@param` interface; dynamic mappings
receive the same validation at render time. A name cannot appear in both
`values` and a fill. Client switching additionally requires statically known
keys and wire-encodable value types.

Citry's existing `make_builtin_components()` factory creates the engine-bound
`<c-trans>` class. The component reads the same engine's i18n extension; using
it while i18n is unconfigured raises a pointed error. This does not require a
new extension component-registration hook. The existing parser already
represents a component call, its attributes, named fills, and source spans, so
a special Rust grammar form would not add information needed by this contract.
Catalog-aware tooling recognizes the built-in component identity and validates
its message key, `values`, and fills from the normal component AST.

The component resolves the message to escaped text segments plus named slot
references and renders the supplied slots in translator-selected order. It must
not concatenate catalog text into trusted `on_render()` HTML. Catalog values
cannot provide HTML, URLs, event handlers, component types, or arbitrary
attributes. Static checking rejects an unknown, missing, or dynamic fill name
and an unknown, missing, or mistyped value. In v1, every reachable resolution
path in the source and each translation emits every required Slot at least once.
A Slot may occur any number of times on one path and in mutually exclusive
selector branches. Each occurrence invokes the same lazy, repeatable Citry
`Slot` separately and creates a distinct rendered subtree and ownership range;
Citry never clones or moves one already-rendered DOM node into two positions.
The compiler rejects only a reachable path that omits a required Slot or uses a
Slot anywhere except a direct standalone `{ $slot_name }` placeable. Browser
insertion, removal, or movement of each rendered occurrence must preserve
component ownership, state, focus, and cleanup. A dedicated parser node becomes
justified only if the prototype proves that ordinary component and fill
metadata cannot support one of those requirements.

Each server-rendered use gets the stable internal key `(rich message instance,
Slot name, occurrence number)`. The server invokes the original lazy Slot once
for each occurrence. Occurrence numbers are counted separately for each Slot
name in output order. Repeated uses of the same Slot have no stronger semantic
identity: if an application must distinguish two stateful uses, it declares two
named Slots instead of repeating one name.

A browser switch cannot currently invoke a Python `Slot` to create another
occurrence. It may only relocate ranges that the server already rendered.
Therefore, v1 requires every browser-selectable translation at one rich call to
emit the same number of occurrences of each named Slot. The order may differ.
A count difference fails the client artifact check and requires a full
navigation. A future server-backed switch may lift that restriction only after
it preserves every surviving keyed range. This restriction does not apply to
server-only rich messages.

The bounded follow-up resolves the ownership question for the equal-count case.
`<c-trans>` does not need a keyed child around the Slot. It invokes the supplied
Slot directly once per occurrence while building `template_data()`. Every call
already creates a separate source-aware `slotRegion`; the component then sends
the small `(occurrence key, Slot name, region ID)` mapping from `js_data()`.
This keeps the original fill's caller scope and gives the browser a stable
physical range for each existing occurrence. No new client-graph record is
needed.

The shipped browser runtime still needs a supported checked operation that
accepts this mapping, validates all ranges and ownership, and relocates the
complete set while updating provider `lang` and `dir` in the same synchronous
commit. Production code must not read private graph maps directly. Cloning DOM
or using the current Events morph is not a substitute. The Events path
recreated surviving nested content and lost focus and teleport-local state in
the earlier bounded exploration.

`<c-trans>` is wrapperless in v1 and therefore cannot attach the selected
message language to its translated text runs. `check` consequently requires
equivalent-language coverage for every selectable locale at every rich call,
including server-only calls; a cross-language rich fallback is an error. Slot
content keeps the language semantics of its application-owned nodes and is not
relabelled as the catalog language. An application that truly needs a
cross-language rich fallback must use an explicit ordinary wrapper plus a
future metadata-bearing rich resolver; that API is not part of v1.

The released Fluent candidates all flatten a resolved pattern to text. The
bounded runtime spike therefore keeps every `Slot` object outside Fluent and
assigns each filled Slot name its own unpredictable, domain-separated marker
for that resolution. Authors and translators write the ordinary
`{ $terms_link }` placeable. The source `@param {Slot}` declaration tells the
compiler that this variable is structural rather than scalar text. In the
generated runtime artifact, the compiler replaces each direct occurrence with
the internal `SLOT($terms_link)` operation. `SLOT` returns that filled Slot's
marker instead of asking Fluent to stringify the Python object; it is not a
function authors or translators call.

One filled Slot name gets one marker for the resolution, and every different
filled name gets a different marker. A translation may repeat or reposition
its bare placeable freely. Every generated `SLOT` occurrence therefore emits
the same marker for that fill. After Fluent returns text, Citry finds all
occurrences, assigns each one an occurrence index, and invokes the original
lazy Slot separately for each position. Every catalog resource in the selected
resolution bundle and every scalar input is collision-scanned against all
markers before resolution. A `Slot` variable is invalid as a selector, term
argument, formatter argument, part of a larger placeable expression, or input
to any other authored function.

The internal `SLOT` step is necessary only because the released Fluent APIs
return a flat string and would otherwise stringify `$terms_link`. It is not
needed to express author intent: the bare variable plus its per-message
`@param {Slot}` type already does that. If a future selected runtime can return
typed structural segments directly, Citry can remove the marker operation
without changing authored FTL.

Fluent-owned bidi isolation is disabled for this operation so Citry can apply
the same internal `CITRY_TEXT` / formatter wrappers to displayed scalars while
keeping only Slot markers unisolated. The runtime spike fixtures exercise that
result, and the compiler/linker spike exercises its tested authored-to-generated
transform. The custom rich-browser reconciler proves the desired range behavior.
The current-runtime explorations then prove that the existing `slotRegion` is
the needed source-aware occurrence record. Citry still lacks the supported
checked relocation operation that uses it.

This marker protocol remains provisional. The runtime spike proves its bounded
raw and decoded hostile catalog cases plus scalar bidi/paragraph rejection, and
the compiler/linker spike proves the tested AST transform and source maps.
Neither proves decoded bidi validation over every linked construct in a
production compiler. The browser follow-up proves the v1 direction boundary:
each client-switchable rich occurrence has one real `<bdi dir="auto">` parent
that contains only its Slot region. Citry does not put `lang` on that boundary,
so application nodes keep their own language markup. A statically known block
root fails `check`; an unexpected runtime block root fails rendering because a
rich Slot is inline content. Teleported content outside the boundary must own
its language and direction at its physical target. Runtime type checks alone
are not enough: all three candidates treated the opaque marker as an ordinary
selector string when the static restriction was removed. Failure of any remaining test
reopens the rich-placeholder notation or keeps `<c-trans>` server-only; Citry
will not implement a private Fluent resolver merely to preserve this API.

### 6.6 Formatting APIs

Message selection and typed value formatting share `LocaleContext` but remain
separate services. Python uses `self.i18n.format`; templates receive a matching
`fmt` global:

```python
self.i18n.format.number(value, format="measurement")
self.i18n.format.percent(value, format="completion")
self.i18n.format.currency(value, "EUR", format="account-balance")
self.i18n.format.date(value, format="short")
self.i18n.format.time(value, format="short")
self.i18n.format.datetime(value, format="audit-event")
self.i18n.format.relative_time(-3, unit="day", format="short")
self.i18n.format.list(values, format="conjunction-short")
self.i18n.format.unit(value, "kilometer", format="narrow")
```

Named formats are typed records compiled into the application manifest. They
prevent copy-pasted option dictionaries and give the server and browser one
parity target. Inline options may exist for application code, but packaged
component contracts use named profiles.

The registry stores application-wide formatting policies, not localized output.
The locale comes from the component's provided `LocaleContext` each time a value is formatted.
For example, the `measurement` number profile can render different digits and
separators in `en-US`, `cs-CZ`, and `ar-EG` even though the profile was declared
once at engine construction.

The engine receives one `FormatRegistry` through the normal built-in extension
settings. Its typed maps are keyed by profile name:

```python
Citry(
    extensions_defaults={
        "i18n": {
            "source_locale": "en-US",
            "locales": ("en-US", "cs-CZ"),
            "formats": FormatRegistry(
                number={"measurement": NumberFormat()},
                currency={"account-balance": CurrencyFormat()},
                date={"short": DateFormat(length="short")},
                time={"clock": TimeFormat(length="medium")},
                datetime={
                    "audit-event": DateTimeFormat(
                        length="medium",
                        time_zone_name="long",
                    ),
                },
                relative_time={"recent-day": RelativeTimeFormat()},
                list={"conjunction-short": ListFormat(length="short")},
            ),
        }
    }
)
```

An application adds a custom profile by choosing a name and placing one of the
supported profile records under its category:

```python
formats = FormatRegistry(
    number={
        "measurement": NumberFormat(),
        "table-value": NumberFormat(),
    },
    date={
        "invoice-date": DateFormat(length="long"),
    },
)
```

Components then use the chosen name:

```python
distance = self.i18n.format.number(
    meters,
    format="measurement",
)
invoice_date = self.i18n.format.date(
    issued_on,
    format="invoice-date",
)
```

Here, “custom profile” means an application-defined name plus a supported
profile record. It does not mean an arbitrary Python formatting function. The
category and record types remain closed so the Rust server and future browser
runtime can implement the same contract. Today `NumberFormat` has no options,
so `measurement` and `table-value` format the same value the same way; the names
still describe why each call site formats that number.

These records are now public Citry classes. Engine construction rejects bad
names, wrong record types, and unsupported options. `TimeFormat` and
`DateTimeFormat` are implemented for the server. Percent and unit records do
not exist yet because their parity contracts did not pass Phase 0. The list
formatter rejects bidi controls, paragraph boundaries, and empty items, then
adds an isolate around each exact item after ICU4X has selected the locale's
conjunction or disjunction grammar.

The call path for `self.i18n.format.number(value, format="measurement")` is:

```text
component i18n facade
    -> read the component's LocaleContext
    -> find the named NumberFormat profile in the compiled registry
    -> pass the locale, profile, and exact number through PyO3
    -> build the matching ICU4X DecimalFormatter in Rust
    -> return the localized string
```

The formatter categories are closed in the current API: number, currency, date,
time, datetime, relative time, and list are implemented, while unratified
categories are rejected. Profile names inside each category are
application-defined, so an
application may add `measurement` or `compact-table` under `number`; it may not
invent a new formatter category by adding another field to `FormatRegistry`.
A framework enum cannot list application-defined names. Tooling should instead
complete and validate the names from the configured registry. A later typed
profile handle or generated `Literal` can give Python callers the same help
without making the names globally closed.

`NumberFormat` and `CurrencyFormat` currently have no option fields. They mean
"use the checked locale-default profile". Two differently named number profiles
therefore produce the same output today; the names still give call sites a
stable application-level purpose. New option fields should be added only after
the Rust and browser implementations pass the same profile tests.

The selected server foundation is ICU4X in Citry's Rust extension. Pin the
exact ICU4X and data-crate versions, enable compiled data and `sync`, and expose
only Citry's named profiles across PyO3. The proof kept exact decimal values,
shaped Arabic and Devanagari digits, used a Buddhist calendar, matched the
checked plural, currency, relative-time, and list results, and supported
concurrent formatter reuse without an external ICU installation.

This selected the foundation, not every direct upstream formatter call. The
checked ICU4X 2.2.0 currency, percent, unit, and relative-time APIs live in
`icu_experimental` 0.5.0. The direct Arabic percent formatter used a different
value convention and percent sign from browser `Intl`; the direct Arabic long-
unit result also missed grammatical output present in `Intl`. Citry hides those
APIs behind its own pinned adapter. The current adapter accepts only the
profiles listed above. Percent and unit remain blocked. Time-zone conversion
does not use an ambient process setting: Citry opens the installed `tzdata`
resource itself, records its version plus a digest of `tzdata.zi`, resolves the
instant in Python, and passes the resulting local fields, offset, timestamp,
and IANA ID to ICU4X.

Babel 2.18.0 and PyICU 2.16.2 remain comparison oracles. Babel's
`numbering_system` changes symbols but did not shape the checked Arabic and
Devanagari digits. PyICU covers the broader matrix, but PyPI publishes no binary
wheel for 2.16.2 and a source build depends on external ICU headers and runtime
libraries. Neither belongs in the production request path. Python's standard
`locale` module is also not a candidate because its C locale is process-global
and unsafe for concurrent request switching.

Strict localized editing is now implemented for numbers. Formatter
construction captures the resolved digit table,
decimal and grouping separators, grouping sizes, and sign affixes from the same
data provider. `self.i18n.parse.number()` uses those same facts and the same
profile name. It returns the untouched input plus a `valid`, `incomplete`, or
`invalid` state; valid values carry an exact `Decimal`. The checked tests cover
Arabic and Devanagari digits, bad grouping, mixed digits, sign-only and
unfinished-group edits. Date/time parsing remains open. Citry must not equate
any one backend `parse()` call with a valid UI editing contract.

The browser implementation uses ECMA-402. A versioned conformance matrix fixes
the locales, calendars, numbering systems, options, time-zone cases, semantic
results, and permitted presentational variation that Citry supports. Exact
string equality is required only for a fixture whose server and browser data
and behavior have been demonstrated to be equivalent. ECMA-402 explicitly
permits implementations and locale data to produce different valid localized
forms, so no general byte-equality promise is possible.

CLDR versions, compiled format metadata, and the effective server tzdb version
or data digest enter output identity; the tzdb identity is also exposed
separately for diagnostics. An unversioned system `zoneinfo` database cannot
satisfy a reproducible profile. Citry does not change `PYTHONTZPATH` or the
process-global zoneinfo search path. It opens the pinned `tzdata.zoneinfo`
resource and constructs `ZoneInfo` with `ZoneInfo.from_file()`, so an installed
system database or `pytz` cannot silently take over. Python documents both the normal
[zoneinfo data sources](https://docs.python.org/3/library/zoneinfo.html#data-sources)
and the
[environment override](https://docs.python.org/3/library/zoneinfo.html#environment-configuration).

Citry constructs every `ZoneInfo` instance through that package-owned source
and passes the resolved local fields and zone facts into the formatter.
The Babel adapter may not call Babel's ambient `get_timezone()` lookup or let an
installed `pytz` package choose a second database. If a future backend uses a
different source deliberately, its package and data revision become part of
the profile and cache identity. This matters because Babel documents that it
prefers `pytz` when available in its
[time-zone support](https://babel.pocoo.org/en/latest/dates.html#time-zone-support).

When the browser's embedded tzdb cannot be pinned, the profile is server-only
or uses a documented fixture/tolerance matrix and forces a reload across an
incompatible server revision.

Templates use the same named profiles:

```html
{{ fmt.currency(total, "EUR", format="account-balance") }}
```

Formatting does not imply parsing:

- Number controls keep a canonical numeric domain value and a separate
  localized edit string. `self.i18n.parse.number()` now defines decimal and
  grouping symbols, signs, digits, whitespace, incomplete states, and errors.
  Exponent notation is outside the current exact-decimal editing grammar.
- Date controls keep canonical date/time domain values. Arbitrary prose such as
  "next Tuesday evening" is outside the first-party parser.
- A `date`, local `time`, local wall `datetime`, and aware instant are distinct
  wire/domain types. A nonexistent local time in a DST gap is rejected. An
  ambiguous fold requires an explicit earlier/later choice before conversion
  to an instant; formatting an already resolved instant is not a gap operation.
- A time-only value formats wall-clock fields only. It rejects an IANA time
  zone and any profile that requests a zone name or offset, because those
  depend on a date. Zone conversion and zone-name formatting require a dated
  local datetime with explicit gap/fold resolution or an already resolved
  instant.
- Currency controls never infer a currency from locale when the domain requires
  an explicit currency code.
- Time-zone conversion of a dated value requires an explicit zone or request
  binding.

### 6.7 Direction and bidirectional text

Locale data supplies a default `ltr` or `rtl`, while the provider permits an
explicit override. The application document shell or real element rendered by
`<c-i18n tag="...">`:

- emits `lang` and `dir` markup;
- exposes direction to component code and the browser context;
- requires Citry UI CSS to prefer logical properties such as inline start/end;
- lets each icon-bearing component declare whether a symbol is semantic,
  invariant, or mirrored;
- isolates unknown-direction variables using `<bdi>`, `dir="auto"`, or an
  equivalent safe formatter contract.

Changing locale does not blindly mirror every arrow. A Back action may mirror;
a media Play triangle, mathematical sign, brand logo, and recorded physical
direction usually do not. Pagination, Breadcrumb separators, Table column flow,
Combobox popup geometry, and keyboard handling each need explicit RTL tests.

### 6.8 Browser delivery and switching

SSR always has the full selected server catalog. Browser behavior has two
delivery modes:

1. **Fixed-locale page:** messages formatted on the server and passed through
   normal escaped HTML need no browser catalog. Browser-only message references
   still pull their statically extracted partition.
2. **Dynamic locale switch:** the client loads the requested locale's manifest,
   message partitions, and format metadata, validates their revisions, then
   commits the new `LocaleContext` and updates parser-recognized `tr()` / `fmt`
   nodes, `<c-trans>` instances, client-owned message references, and the
   provider's `lang` / `dir` wrapper atomically. Every target must be owned by
   an explicit `<c-i18n client tag="...">` boundary.

Arbitrary `self.i18n.tr()` and `self.i18n.format.*()` results returned from
Python are ordinary SSR strings. Citry does not serialize `template_data()`,
and the browser has neither their formatter inputs nor a DOM target. They
therefore change locale only through normal navigation or an explicit
server-fragment rerender. In-place switching is limited to template operations
that the V3 AST records in the closed direct-call subset from section 6.5 and
explicit `ClientMessageRef` / `ClientFormatRef` records returned from
`js_data()`, each with a validated ID or profile, typed wire operands, and a
stable Citry ownership marker. Finding a literal call nested inside a larger
Python expression is extraction information, not permission to replay that
expression in JavaScript. A server-fragment transaction is a parked
alternative, not an implied capability.

The versioned client-value wire format is tagged strict JSON, not a direct
dump of Python objects. Its initial closed set contains text, booleans, null,
integers and `Decimal` values as canonical decimal strings, finite Python
floats as tagged IEEE-754 binary64 bit patterns, date-only fields, local-time
fields, resolved instants as a signed epoch-millisecond decimal string plus
zone ID, explicitly disambiguated local datetimes, and recursively typed lists.
A float uses exactly 16 lowercase hexadecimal digits in network bit order, for
example a tag shaped like `{"type":"f64","bits":"8000000000000000"}`;
the client reconstructs those bits with `DataView`, preserving negative zero.
NaN and either infinity are rejected. Decimal never passes through this float
tag. The initial instant profile is bounded to ECMA `Date`'s exact integer
range and rejects sub-millisecond precision. The wire also rejects unknown
objects, naive datetimes where an instant is required, unresolved DST
gaps/folds, and values outside the declared ECMA-402 profile. The client adapter
reconstructs the semantic value without an intermediate lossy JavaScript number
conversion; unsupported browser representations make that profile server-only.
Every browser operation has a statically inferred operand type and range or
fails the production check. Temporal tags carry calendar and zone IDs
explicitly where applicable; locale never supplies either as hidden domain
input.

Client-owned component behavior must retain message identity, not only the
string resolved during SSR. `self.i18n.client_message(...)` and
`self.i18n.client_format(...)` are proposed server helpers that emit the typed
references for `js_data()`. Client message code binds each reference to its
declared element/target through `bindMessage()` and receives atomic text plus
selected-locale metadata updates; client format references that cannot change
language subscribe to ordinary context commits. Literal component props remain
literal and do not switch. This migration is required for current Pagination
and Combobox JS, which persist labels in `js_data()` and later write them back
to the DOM. Without typed references and registered sinks, those components are
navigation-only.

Artifacts are partitioned by package and feature, then bundled by the build
adapter according to statically known references. They are not fetched once per
component instance. Each defining owner's source locale and accessibility-
critical fallbacks are available without a second network round trip where
dynamic switching is enabled.

If loading fails, the client keeps the prior locale and content, exposes a
diagnostic event, and lets the application present a retry. It never commits a
new `lang` or `dir` while leaving old messages in place.

Concurrent switch requests receive monotonically increasing generations. Only
the latest requested generation may commit; a completed stale load is ignored,
and cancellation or failure leaves the last committed context intact.

The client manifest's canonical locale table is generated from the same Rust
canonicalizer used by Python bindings and records its data/schema revision.
Canonical IDs are always accepted. Additional client spellings or deprecated
aliases are accepted only when the generated alias map names them; application
configuration can request an alias, but Rust validates that it maps into the
configured selectable set. This intentionally bounded contract prevents two
browsers with different ICU versions from choosing different targets for the
same `switchLocale()` input.

### 6.9 Cache rules

Locale is not added mechanically to every cache key.

| Cache layer | Rule |
|---|---|
| Parsed or compiled Citry template | Locale-neutral. It stores executable structure, not localized output. |
| Compiled message catalog | Key by locale, catalog source digest, backend/compiler version, and relevant CLDR or function revision. |
| Output or fragment cache | The author includes every localized-output input in ordinary `Cache.vary()` or `<c-cache vary>`, just like any other ambient fact. Cache does not know about i18n. |
| Constant-body cache | Remains neutral when the constant stores structure. If localized output is precomputed as a constant, its signature must include the locale and relevant revisions. |
| ECMA-402 or Python formatter constructors | Reuse by locale plus normalized options. Do not cache final user-specific strings under that constructor key. |

Cache lookup occurs before component `template_data()`. `Cache.vary()` already
runs at that point and can read public extension data through
`self.component`. A localized component includes the i18n context's plain
identity explicitly:

```python
class Cache:
    enabled = True

    def vary(self, kwargs, slots):
        return {
            "kwargs": kwargs,
            "locale_context": self.component.i18n.context.identity,
        }
```

`LocaleContext.identity` is an ordinary versioned tuple containing locale,
intermediate fallbacks, direction, time zone, tzdb revision, catalog revision,
and formats revision. Cache's existing canonical encoder handles it without an
i18n import or a special token type. A fragment receives the same value through
ordinary template data and passes it to `c-vary`.

If the author omits that value, Cache follows its normal rule and may share the
entry across locale contexts. This is the same responsibility as omitting a
user, tenant, feature flag, or current-time bucket. I18n tooling may point out a
localized cached component whose variation looks incomplete, but the runtime
contract does not add i18n-only fields to Cache or change `Cache.vary()` based on
which extensions are installed.

Like every extension, i18n declares its behavior through the core render-cache
compatibility contract. This is one generic hook, not an i18n branch inside
Cache. The leading contract is `render_cache_mode = "stateless"` and
`render_cache_version = 1`: settled HTML plus existing dependency/ownership
artifacts must capture every effect, while compiled catalogs stay outside the
render artifact. Phase 0 must prove that claim for client references, providers,
provider wrappers, and diagnostics. If any render-scoped i18n effect is not
captured, i18n changes to `"payload"`; it must never fall through to the
conservative `"deny"` default merely because the built-in is dormant.

## 7. `citry-ui` contract

### 7.1 Precedence

For every library-authored string:

1. an explicitly supplied component prop or slot;
2. the stable ID resolved by the locale-major, application-before-library
   algorithm in section 6.1;
3. the exact `citry-ui` English source literal when i18n is unconfigured.

This mirrors the useful provider-plus-local-override pattern in MUI X while
keeping existing Citry UI calls compatible. Installing i18n must not change an
explicit prop.

`citry-ui` may use the stable built-in surface at `self.i18n`. When the engine
has no i18n configuration, the helper selects the English source default.
When configured, `self.i18n.tr()` sees the request and nearest provider context.

Presence, not equality or truthiness, defines an explicit override. The helper
checks `field_name in self.raw_kwargs` and the corresponding raw-slot presence
before it consults the normalized dataclass value. This preserves an explicitly
supplied English literal even under a non-English locale. A future public unset
sentinel is an alternative only if it preserves the current typed string API.

### 7.2 Current authored-string inventory

The current production code contains 18 overrideable English defaults and one
non-overrideable English format:

| Family | Current source-owned output | Required action |
|---|---|---|
| Breadcrumbs | `Breadcrumbs` | Add message ID; retain the label prop; record the visible-string inventory in the spec. |
| Pagination | `Pagination`, `Page {page}`, `Previous page`, `Next page`, `First page`, `Last page` | Add six IDs and extracted variables; retain every prop override; replace persisted `js_data()` label strings with client message references before enabling in-page switching; test RTL controls separately. |
| Table | `Loading data...`, `No data.`, `Unable to load data.` | Add three IDs; retain loading, empty, and error slots/props. |
| Combobox | `Select an option.`, `Clear selection`, `Show options`, `Hide options`, `Loading options...`, `No options found.`, `Options could not be loaded.` | Add seven IDs; preserve explicit inputs; replace persisted `js_data()` labels with client message references before enabling in-page switching; add collation/filtering as a later behavioral contract. |
| Dialog | `Close` | Add one ID; retain close-label override. |
| Progress | `"{label}: {value:g} of {max:g}"` | Preserve this exact path when i18n is unconfigured. When configured, replace the hard-coded `of` composition with a message ID and locale-aware number formatting; add the missing spec inventory. |

Library-authored visual symbols also require review even when they are not
translated prose: Breadcrumbs `/`; Pagination `«`, `‹`, `›`, `»`, and `…`;
and ASCII page-number output. The review decides logical direction, mirroring,
typography, and numeric formatting for each symbol.

Tabs currently has no built-in close or overflow label. Such future labels must
enter the inventory when the feature is added; they are not existing migration
work.

### 7.3 Component specification requirement

Every Citry UI specification must list:

- visible source-owned strings and their interpolation variables;
- accessibility-only strings and related visual/a11y attributes;
- string props and slots that override defaults;
- numbers, dates, times, units, lists, or comparisons it formats;
- locale-sensitive parsing, filtering, sorting, or keyboard behavior;
- direction-sensitive layout, symbols, and keys;
- expected behavior with i18n unconfigured;
- expected fallback and diagnostic behavior with i18n configured.

This inventory is a prerequisite for new component implementation, not a
cleanup after release.

## 8. Extraction, checking, and build outputs

The extension uses Citry's existing command namespace:

```text
citry ext run i18n extract
citry ext run i18n check
citry ext run i18n compile
citry ext run i18n inspect
```

The current commands are:

- `extract`: print the deterministic source-unit index. Translator-facing file
  generation is still later work;
- `check`: compile and validate the complete project graph without rendering a
  component, then print the catalog and format revisions;
- `compile`: write the checked manifest and server artifact for each named or
  configured standalone catalog package. Browser partitions are still later
  work; and
- `inspect`: print the complete checked project artifact, or write it to the
  path supplied through `--out`.

Registry-backed `citry check` also uses the same compiler. It reports invalid
catalogs, unknown literal message values and attributes, wrong or missing
literal `tr()` arguments, wrong `<c-trans>` values and fills, invalid
`Component.I18n.client_messages`, unsafe cross-language plain-text fallback,
and the configured missing-parameter-type severity.

All four commands start from one deterministic project inventory. Batch mode
loads configured catalog-package manifests and runs normal Citry component
discovery, then reads every registered component's `messages` /
`messages_file`. Local component sources are parsed directly. The result is an
in-memory catalog graph; the tool does
not need to write or reread one combined FTL file first.

That complete graph is the authority for literal keys. A literal ID or
attribute used by `tr()`, `self.i18n.tr()`, `<c-trans>`, a client message
reference, or an inspected JavaScript sink that is absent from the graph is a
hard `citry.i18n.unknown-message` error at the use site. A duplicate definition
reports both definition spans. Finite typed dynamic IDs are checked by expanding
their declared member set against the same graph; arbitrary computed strings
remain outside static proof and use the documented runtime API contract.

An editor keeps the same graph as a live project index and updates the affected
source unit and its dependants after an edit. It does not report an unknown-key
error while relevant component discovery or package indexing is incomplete;
instead it marks the i18n project index incomplete and reruns the check when the
inventory becomes authoritative. This prevents false errors during startup
without weakening batch `check` or production compilation.

Extraction uses Python AST, the Fluent AST, and Citry's V3 AST rather than
guessing from text. The current checker parses literal template `tr()` calls as
Python expressions and reads `<c-trans>` attributes and named fills from the V3
tree. The Rust compiler reads message IDs, attributes, variables, references,
selectors, `@param` types and descriptions, and their source spans from the
Fluent tree. Future editor metadata can reuse those exact records.

The first Python extractor accepts literal IDs in direct
`self.i18n.tr(...)` calls, including a literal `attr=...`. Checking literal
named profiles in `self.i18n.format.*(...)` calls remains future work. The
extractor need not follow arbitrary aliases, containers, returned facades,
reflection, or dynamically constructed method calls. The template extractor
currently accepts literal IDs in built-in `tr()` calls and reads `<c-trans>`
fill structure from the V3 tree. Its planned browser form also accepts the
typed `ClientMessageId` enum operand below and literal profiles in the built-in
`tr()` and `fmt` surfaces. A dynamic ID becomes browser-eligible through
`Component.I18n.client_messages` only when the complete direct call captures
that typed enum
operand from section 6.5. An arbitrary string expression does not qualify, and
the allowlist does not make surrounding Python client-executable. The extractor
separately records whether the complete output or attribute expression belongs
to the closed direct-call subset; a reference to `self.i18n` alone contains no
message ID.

The generated artifact manifest records at least:

- package, package version, defining owner, and owner source locale;
- selectable and fallback-only locale declarations;
- canonical selectable IDs, accepted client aliases, and the shared
  canonicalizer's data/schema revision;
- catalog layer and partition;
- message IDs, attributes, direct and transitive parameter interfaces with
  concrete or unknown static type, translator descriptions, missing-type lint
  state, required resolved outputs, and source locations;
- browser-required IDs and dynamic-ID allowlists;
- client message/format references, message sink IDs/targets, and tagged
  operand schemas;
- client-executable AST shape and captured operand types;
- provider wrapper targets and nested provider-policy records;
- named format profiles;
- rich-placeholder required-presence, repeatability, and allowed-nesting contracts;
- message compiler, CLDR, tzdb source or digest, and artifact schema versions;
- content revisions and fallback graph.

The primary `messages_file` pair extends Citry's existing asset loader instead
of inventing an extension-private file path. Its acceptance tests cover
declaration-site anchoring through inheritance, UTF-8 decoding, inline
dedenting, missing files, wheel resources, watcher registration,
catalog-cache eviction, and one atomic last-good reload.

## 9. Failures and diagnostics

| Failure | Required behavior |
|---|---|
| Invalid catalog resource name, descriptor, locale directory, duplicate resource, unimportable package, descriptor/manifest identity mismatch, duplicate stable owner, or missing descriptor or generated manifest | Reject engine construction or production build and name the configured entry, path, and expected descriptor or manifest field. |
| Invalid source catalog or `messages` / `messages_file` declaration | Fail component definition, engine startup, or build at the earliest deterministic point with source span. |
| A supported Fluent node has no exact source range, or a source map does not match its catalog revision | Fail compilation and emit no catalog artifact; never use an entry-start or guessed range. |
| A simple server-only scalar variable lacks `@param` metadata | Emit `citry.i18n.missing-param-type` using the effective `rule_i18n_missing_param_type` severity, which defaults to `warning`; `ignore` suppresses it and `error` fails checking. |
| A `Slot`, selector, formatter, client operand, or other type-dependent operation lacks a concrete `@param` type | Fail extraction/check regardless of lint severity because the operation cannot be proved correct. |
| Malformed, duplicate, unused, or unsupported `@param` annotation | Fail extraction/check at the source message and variable; never evaluate annotation text as Python. |
| Call-site value is incompatible with the extracted Python parameter type | Fail at the known call-site span and cite the defining `@param` span. |
| Literal message ID or attribute is absent from the complete project catalog graph | Fail at the Python, template, `<c-trans>`, or client-reference use site with `citry.i18n.unknown-message`. An editor defers this diagnostic while its project index is incomplete. |
| Invalid `Component.I18n` field, duplicate client message ID, unknown ID, or inherited client behavior missing an ID after replacement | Fail component definition or production check with the effective config owner. |
| Canonically duplicate locale, unknown fallback node, cycle, duplicate defining owner, missing owner source catalog, or unresolvable owner source output | Reject engine construction/build with the complete offending owner and chain. |
| Duplicate ID in one catalog layer | Error. Never let file order decide. |
| A public-reference closure gives one variable incompatible types, adds an undeclared input, or omits a required Slot on a reachable path | Fail catalog linking and report the complete reference path plus every conflicting source span. |
| Translation introduces an undeclared variable or violates required rich-placeholder structure | `check` and production build fail. Using a subset of source variables is valid. |
| `<c-trans>` has an unknown, missing, mistyped, or colliding `values` entry or fill | Fail `check` at the component call and cite the defining `@param` parameter. Dynamic server values receive the same check at render time. |
| Missing defining-owner source value used by code | `check` and production build fail. Development render raises a contextual error. |
| Missing secondary-locale message or attribute | Follow intermediates, then the defining owner's source locale; record a structured diagnostic. Partial attribute translations are valid when this resolves every required output. |
| Missing accessibility attribute after all fallbacks | Fail the production check for library-declared required attributes. Do not render an ID as an accessible name. |
| Cross-language fallback at a text-only, wrapperless rich, client-switched, or accessibility call site | Fail the production check unless every selectable locale has equivalent-language coverage. Development may render plain directionally isolated text with a structured diagnostic; wrapperless rich output still fails because it cannot carry selected-language metadata. |
| Unknown explicitly requested locale | Raise a typed configuration or request error. |
| Browser locale is absent from the versioned canonical-ID/alias table | Reject `switchLocale()` without loading artifacts or changing the current context. |
| Unsupported negotiation candidate | Continue through candidates, then use the configured default locale; each message lookup still ends at its defining owner's source locale. |
| Unknown or invalid time zone | Raise a typed error; do not silently use the server's local zone. |
| Invalid date, number, currency code, or other typed formatter input | Raise a typed formatter error naming the profile and value type; do not coerce through server defaults. |
| Unsupported calendar, numbering system, or format option | Reject a named profile at build/startup; reject a truly request-dynamic option at the call site. |
| Missing or mistyped message variable | Strict development error. Production uses the validated defining-owner source fallback only if one can be rendered safely; otherwise emit the configured error boundary and diagnostic. |
| Built wheel omits or changes a descriptor, source, or artifact named by the generated manifest | Package verification and production build fail with the wheel path and missing or mismatched package-data path. |
| Missing or corrupt packaged catalog/manifest | Production build or engine startup fails for a configured server layer. A dynamic browser load keeps the prior locale. |
| Browser catalog or format chunk load failure | Keep the prior locale atomically and notify the application. |
| Server/browser revision mismatch | Refuse the new browser context and request a full reload or compatible artifact. |
| Unsupported formatter option or deliberate server/browser difference | Fail manifest validation unless the profile documents and tests a server-only use. |
| Browser operand has unknown/lossy type, unresolved gap/fold, or unsupported range | Fail production check or render before artifact emission; never coerce through plain JSON numbers. |
| Reserved template name collision for `tr` or `fmt` | Fail definition/configuration and report both owners through namespace introspection. |
| Client-bound template expression is outside the closed direct-call subset | Fail the production check with the expression span; do not ship a node that becomes stale after switching. |
| A dynamic ID enum member lacks the selected attribute, rejects a supplied variable/type, or needs an unsupplied variable | Fail compilation at the call site and name every incompatible enum member. |
| `ClientMessageRef` sink has no unique registered target or lacks equivalent-language coverage | Fail the production check; do not expose a bare switchable string. |
| Client i18n consumer is below `client=False` without a nearer `client=True` provider | Fail ownership validation; do not inherit the outer client service. |
| A localized cached component omits output-affecting context facts from ordinary variation | Follow normal Cache semantics. Tooling reports the likely omission where it can prove the dependency; the author must add `self.component.i18n.context.identity` or leave caching disabled. |

Diagnostics are structured records suitable for logs and test assertions.
Applications decide telemetry and end-user presentation.

## 10. Security and privacy

- Catalog variables are escaped by default and retain their type until the
  formatter consumes them.
- Translation files cannot provide raw HTML, script, style, event-handler
  attributes, component names, or arbitrary URLs.
- Rich messages accept only named, source-declared placeholders supplied by
  application code.
- Bidi isolation protects interpolated user, product, path, email, and numeric
  values from changing surrounding ordering.
- Decoded catalog AST values reject literal or escaped `Bidi_Control`; inline
  untrusted scalar inputs also reject every bidi paragraph boundary.
  Compiler-owned balanced isolate controls are introduced only by generated
  formatting operations.
- Locale candidates from headers, cookies, URLs, or profiles are canonicalized
  and matched against the configured set before they reach file paths or module
  loading.
- Diagnostics must not record translated variable values by default; they may
  contain personal data.
- Catalog artifact paths derive from manifest IDs, never raw request input.

## 13. Alternatives considered

### Optional package instead of a built-in extension

Not preferred. I18n needs coordinated access to primary component assets,
template data and AST metadata, render and subtree context, dependency emission,
commands, and browser ownership. It composes with Cache through ordinary public
variation data rather than a private bridge. That is the same class
of framework integration that justifies built-in Cache, Dependencies, and
Events. A dormant built-in also gives every component the predictable
`self.i18n` surface.

The message/CLDR backend may still be an optional dependency if package-size or
platform evidence requires it; that does not require moving the integration
contract out of Citry.

### Put message source inside `class I18n`

Not preferred. `messages` / `messages_file` is the fourth primary authored asset
pair beside template, JS, and CSS, so it stays directly on the component and
uses the same loading, inheritance, watching, and hot-reload rules. The nested
`class I18n` has a different job: it contains ordinary per-component extension
settings, beginning with `client_messages`. This keeps authored content in the
familiar asset position without putting an extension setting at component top
level.

### Use source English as message IDs

Rejected. It makes copy edits identifier changes, complicates application
overrides, and cannot give attributes and variables a stable contract. Stable
semantic IDs are more verbose and are better library API.

### Use simple dictionaries instead of a message language

Rejected as the complete solution. Dictionaries work for UI labels, as shown
by many component libraries, but push plural, gender, agreement, reordering,
and formatted-value decisions into application code. A dictionary adapter may
still be sufficient for a deliberately narrow library-message provider.

### Standardize immediately on ICU MessageFormat 2

Parked. MessageFormat 2 is promising and standards-oriented, but the current
ICU API still labels important parts as technology preview and its final
function/parameter set is not fully settled. See the
[ICU MessageFormatter API](https://unicode-org.github.io/icu-docs/apidoc/dev/icu4j/com/ibm/icu/message2/MessageFormatter.html).

Reevaluate before backend ratification. If the Python and browser
implementations are mature, interoperable, and diagnostically stronger than
Fluent at prototype time, prefer the more portable standard.

### Publicly support arbitrary message backends in version one

Rejected. A small internal engine protocol is useful for prototype comparison,
but a public adapter API would freeze message IDs, attributes, rich placeholders,
format hooks, fallback, compilation, and diagnostics before Citry has usage
evidence. The application-level translator integration can be considered after
one first-party backend works end to end.

## 14. Open decisions and falsifiers

These gates block ratification, not the bounded prototypes. No benchmark or
backend comparison begins until a `prototype-environment.md` records the exact
Python and browser package versions, lockfile digest, Python and browser
versions, machine description, commands, and fixture manifest. Changing any of
those inputs starts a new evidence run.

### 14.1 Fixed conformance matrix

The initial matrix is:

- locales `en-US`, `cs-CZ`, `ar-EG`, `ru-RU`, `pl-PL`, `ja-JP`,
  `az-Latn`, `az-Arab`, `hi-IN-u-nu-deva`, and
  `th-TH-u-ca-buddhist`;
- Latin, Arabic-Indic, and Devanagari numbering; Gregorian and Buddhist
  calendars;
- Arabic cardinal categories `zero`, `one`, `two`, `few`, `many`, and `other`;
  Russian and Polish `one`/`few`/`many`/`other`; Czech
  `one`/`few`/`many`/`other`, including fractional operands;
  English ordinal categories; and exact numeric selectors `0`, `1`, `2`, `3`,
  `5`, `11`, `21`, and `101`;
- `Europe/Prague` spring gap `2026-03-29 02:30` and fold
  `2026-10-25 02:30`, plus `America/New_York` gap `2026-03-08 02:30` and fold
  `2026-11-01 01:30`; each is a local-wall-time input, gaps must reject, and
  folds must reject without an explicit earlier/later choice before converting
  to the expected instant;
- decimal, percent, currency, unit, list, relative-time, date, time, datetime,
  plural, select, message attribute, term, rich-placeholder, bidi, fallback,
  and missing-value fixtures;
- transparent server providers with rootless and multi-root output, client
  providers with valid real-element wrappers, slots, retained ranges, morphs,
  teleports, concurrent requests, nested inherited/explicit provider policies,
  true/false/true client-provider barriers, and latest-generation client
  switches;
- an application with source `cs-CZ` plus `citry_ui` with source `en-US`,
  including application overrides of library-owned IDs in active and fallback
  locales, selected-source plural/term evaluation, `LocalizedText` fallback
  metadata, and equivalent-language completeness checks.

For every declared cross-runtime profile, server and browser must agree on the
semantic result: selected plural or message branch, sign and numeric value,
currency or unit identity, calendar fields, instant and time-zone meaning,
list membership and order, and visible/accessibility ownership. Exact
normalized string equality is additionally required only for fixtures whose
runtime data and output behavior are shown to be equivalent. Every other
profile records a bounded accepted-output set or explicit tolerance justified
by ECMA-402 implementation dependency. A profile with an unpinnable browser
tzdb or unbounded difference becomes server-only; it cannot be called generally
parity-safe.

### 14.2 Backend and diagnostic gates

A message or formatting backend passes only if:

1. its latest stable release or maintainer commit is no older than 18 months at
   ratification, it supports every Python version in Citry's current CI range,
   and it has no unmitigated high or critical advisory;
2. it passes every applicable fixture above without a Citry-side fork of the
   selected message grammar; V3 authoring grammar may change independently;
3. every message-runtime number/date/plural operation delegates to the same
   normalized Citry formatter contract as the direct API, and every translator-
   selectable option is allowlisted and cross-runtime validated;
4. every catalog syntax diagnostic reports file, one-based line and column,
   and message ID when an ID was parsed; missing variables and attributes also
   report the Python or template use site when extraction knows it;
5. the dynamic runtime plus a 100-simple-message partition is at most 35 KiB
   gzip, and each additional 100-message locale partition is at most 15 KiB
   gzip. A catalog parser may ship only inside an explicit client-switching
   boundary when the supported public runtime API requires source input; all
   source is still validated and compiled at build time. Before parsing, the
   client verifies the artifact digest plus declared runtime revision. The
   build runs the exact pinned browser parser/runtime against canaries covering
   every reachable public ID, attribute, private term, message reference,
   function, selector, and variant, and records their transitive manifest.
   After parsing, the client verifies that manifest and formats every reachable
   canary operation/branch before commit. Any discrepancy or resolution error
   aborts the atomic switch. The browser parser is never treated as a
   validator, and a fixed-locale page remains parser-free.
   A private upstream AST is not a compiled-artifact contract unless Citry owns
   a versioned schema plus compatibility canaries;
6. the fixed-locale page ships zero i18n browser bytes unless it contains an
   explicit `<c-i18n client tag="...">`; client-switching nodes outside that
   boundary fail the production check;
7. a backend claiming the full matrix shapes and parses every declared digit
   system without undocumented post-processing. Babel may pass only a named
   subset unless a separate shaping candidate passes the same gates.

Failure rejects that backend or narrows the first release to a server-only
surface. The selected Fluent runtime is not an exception to these gates.

### 14.3 Performance procedure and thresholds

The benchmark compares a literal-string component tree with an equivalent tree
containing 100 warm message resolutions and 20 named format calls. Each backend
gets five warmups and 30 measured samples in one process; backend order is
rotated. One backend run has a 15-minute budget and the complete matrix has a
two-hour budget. Record median, p95, peak resident memory, catalog build time,
artifact bytes, and sample dispersion.

The warm localized tree passes when added median render time is no greater than
`max(15% of literal baseline, 2 ms)` and added p95 is no greater than
`max(20% of literal baseline, 3 ms)`. A loaded 100-node client switch must have
p95 commit time at or below 50 ms over 30 samples in each supported browser,
with zero sampled frames containing a mixed committed locale. Unconfigured
Citry must show zero loaded catalogs and browser bytes, and its render timing
must stay within the literal benchmark's 95% confidence interval.

The final bounded Phase 0 run passed these thresholds. The measured dynamic
client plus 100 simple messages was 11,344 bytes gzip, a second 100-message
locale partition was 511 bytes gzip, and fixed-locale server output loaded no
i18n browser bytes. The production-shaped tree added 1.49 ms median and 1.51 ms
p95 on the recorded machine. Loaded locale-change p95 was 0.4 ms in Chromium
and 1 ms in Firefox and WebKit, with no sampled mixed frame. These browser
numbers exclude network time. The server formatter was still a deterministic
stand-in, so the final ICU4X adapter must repeat the server matrix.

### 14.4 Citry integration falsifiers

1. **Authoring:** `messages` / `messages_file` must preserve declaration-site
   file resolution, inheritance, UTF-8 and dedent rules, watcher registration,
   hot reload, extraction, and source spans. `@param` types must round-trip into
   manifests with per-message scope. Malformed, unused, or incompatible
   declarations must fail; a missing simple scalar declaration must follow the
   configured lint severity, while every type-dependent operation must still
   fail without a concrete type. Reusing one variable spelling with different
   types in unrelated messages must pass. The complete project graph must find
   cross-component and standalone-package IDs, reject unknown literal uses, and
   report both definitions of a duplicate public ID without relying on one
   concatenated source file.
   Catalog strings must resolve import-package resources and stable manifest
   owners without confusing them with distribution names. Generated `citry-ui`
   English defaults must byte-match authoritative FTL. Failure reopens
   external-only sources or another authoring shape.
2. **Provider:** request and subtree state must remain isolated and correct for
   every ownership case in section 14.1. Failure blocks the subtree provider or
   requires an explicit client-graph protocol change. A standalone `<c-i18n>`
   with `client=False` must emit no i18n client data or dependencies; below an
   enabled ancestor it must make the browser i18n service unavailable to its
   subtree without loading an i18n runtime or catalog. The outer service must
   not cross that boundary. `client=True` must be known before
   descendant rendering. True/false/true nesting must create two independent
   client boundaries, and nested enabled policies must recompute outer-to-inner,
   preserve explicit fields, and stage every provider wrapper's `lang` / `dir`
   update in the same commit as content. A core client provider without a valid
   real-element wrapper must fail before browser artifacts are emitted.
3. **Cache:** when an author puts `LocaleContext.identity` in component or
   fragment variation, it must distinguish locale, fallback, direction,
   time-zone, tzdb, catalog, and format inputs. One cross-locale hit with that
   identity present rejects the design. Omitting it follows ordinary Cache rules
   and deliberately permits sharing. Cache must not import i18n, add an i18n
   config field, or change the `vary(kwargs, slots)` signature. The built-in must
   also pass `stateless` version-1 replay tests or switch to a defined payload
   mode.
4. **Layering:** the pseudocode in section 6.1 must produce the asserted winner
   for every active/intermediate/owner-source locale and application/library
   layer, including different package source locales. An override must not
   change defining ownership. The returned pattern must evaluate with the
   selected locale's plural and formatter rules and selected bundle's
   private-term scope; transitive public references must resolve at that same
   locale or make the candidate continue fallback. Any file-order-dependent
   result, mixed-locale text projection, or active-locale evaluation of a
   fallback pattern rejects merged layers.
   The bounded compiler/linker spike proves deterministic internal IDs,
   operation mappings, public-reference precedence, per-output transitive typed
   interfaces,
   same-name type-conflict diagnostics, required and repeated `Slot` handling,
   layer-private terms, cycle diagnostics, and identical Python/browser/Rust
   execution for its tested subset. Production must preserve those results
   across the complete supported Fluent subset and browser artifact schema.
   The extended production-shaped slice combines those results across a real
   Rust/PyO3 wheel. It proves deterministic artifact discovery, four-of-four
   warm parsed-catalog reuse, one-of-four selective reparsing, selector and
   formatter generation, path-aware repeated Slots, and exact authored and
   generated byte ranges for all eight tested operation kinds. The positioned
   `Slice` now runs inside the compiler rather than in a separate parser probe.
   Production must preserve those results as it expands the supported Fluent
   subset and replaces the test formatter service.
   Executing only a hand-generated fixture remains insufficient.
5. **Parser/binding:** literal call metadata and closed client-executable shapes
   must preserve spans and deterministic output across the Rust AST/compiler,
   PyO3, stubs, wrappers, runtime nodes, and Rust/Python tests. Ordinary
   `<c-trans>` calls must retain the existing component and named-fill shape
   needed by catalog-aware tooling without a special parser node. A typed
   dynamic message ID must be confined to its finite manifest allowlist, and
   every member must pass the call site's attribute, variable, and type
   interface. Accepting composed arbitrary Python for client replay or any
   unexplained binding drift rejects the syntax candidate.
   The production-shaped slice confirms that current V3 output retains direct
   expression spans and ordinary component/fill structure, and that a Python
   metadata pass can classify direct literal `tr()`, composed `tr()`, and
   dynamic IDs. It does not yet prove the final single Rust/PyO3 metadata owner.
6. **Client switching:** only recorded V3 i18n operations, `<c-trans>` instances,
   and typed client references under `<c-i18n client tag="...">` may update
   without a server render. Wire
   values, including signed-zero binary64, must round-trip without loss. Locale
   inputs must resolve through the versioned canonical-ID/alias table, not
   ambient browser ICU. A stale generation, failed chunk, or revision mismatch
   must leave the previous context, provider wrappers, client consumers, and all
   visible/accessibility output unchanged. Text-only and accessibility sinks
   must prove equivalent-language coverage across the selectable set; an
   unbound reference rejects the client artifact. A client-switchable rich call
   must keep the same occurrence count for each named Slot across its selectable
   locales. The real ownership graph must preserve the original fill's caller
   scope while relocating every surviving keyed range. Any clone, missing
   source owner, recreated surviving subtree, duplicate cleanup, lost focus, or
   partially committed `lang` / `dir` rejects the client-rich path.
7. **Citry UI compatibility:** with i18n unconfigured, every current call
   renders its exact existing English output. With i18n configured, an
   explicitly supplied prop or slot, including one equal to the English
   default, must win in every locale. Progress retains its current `:g`/`of`
   fallback only in unconfigured mode, while Pagination and Combobox may not
   restore stale labels after a client locale commit.

## 15. Completion criteria

The i18n foundation is complete enough to unblock general UI work when:

- the built-in extension and locale context are ratified and implemented;
- messages and every profile declared cross-runtime meet the semantic and
  bounded presentational agreement rules on server and browser; server-only
  profiles are marked and tested as such;
- source extraction, validation, compilation, per-package owner/source
  manifests, per-message `@param` interfaces and missing-type lint policy, the
  complete project catalog graph, `Component.I18n` config, and fallbacks run in
  CI;
- all current Citry UI authored strings have stable IDs, extracted source
  interfaces, English fallbacks, application overrides, pseudo-locale evidence,
  and RTL review;
- localized component and fragment caches explicitly include
  `LocaleContext.identity` through ordinary variation data, locale-independent
  entries deliberately omit it, and constant, catalog, and formatter caches
  pass their layer-specific isolation tests;
- the client wire, canonical locale map, readonly service, provider barriers
  and policies, real provider wrappers, bound message sinks, and Citry UI client
  message consumers pass atomic-switch tests;
- dynamic switching is either production-ready or explicitly excluded from a
  server-only first release;
- NumberInput has a ratified strict parsing contract;
- date/time controls have a ratified date-library, calendar, time-zone, and
  canonical-value contract.

This criterion unblocks component design. It does not imply that Citry or
`citry-ui` ships translations for every locale or every future control.
