- **Reviewer:** a separate reviewing agent, in three rounds
- **Code:** `Citry.build_url()`, and the functions each integration's

## Who controls the input

An app served below a sub-path, such as `/shop`, now has Citry start its own
URLs with that sub-path. The sub-path can come from request data: a proxy
header such as `X-Forwarded-Prefix`, read through `ProxyFix(x_prefix=1)` or
a user middleware, so a client may be able to set it. The browser loads the
URLs Citry writes (script and stylesheet tags, the page's JSON manifest,
the fragment preloader) and sends event calls to them. A value that a
client sets must not make the page load code from another site, break out
of an attribute or a script element, or reach another request's page or
cached HTML.

## How it was checked

The reviewer drove Chromium against real servers: uvicorn running a FastAPI
app and werkzeug running a Flask app. It sent 48 crafted sub-paths, each
set both directly and through `X-Forwarded-Prefix`. They included values
that try to name another host, quote and script-tag breakouts, encoded
dots, control characters, a `javascript:` URL, and a 20 kB value. Each one
was followed to every place it can end up:

- the script and stylesheet tags;
- the page's JSON manifest;
- the fragment preloader's script literal;
- the Events endpoint and base URL;
- `events.url()` in a cached template;
- the render cache (the rendered HTML Citry stores and reuses across
  requests).

## Ruled out

- **Loading from another site:** no request left the page's origin. A
  sub-path that does not start with a single `/` counts as the site root.
- **Injection:** no injected script ran, and no value escaped an attribute
  or the JSON script element. A sub-path's characters outside those allowed
  in a URL path are percent-encoded.
- **Carry-over between requests:** no crafted sub-path reached another
  request's page, Events response, or cached HTML. The render cache keeps
  separate entries for each sub-path.
- **Pointing the page at another path on the same site:** when the app
  trusts a prefix header that any client can set, that client can make the
  page's URLs point at a different path on the same site, such as an
  upload folder. Citry cannot tell a proxy's header from a client's, so the
  deployment decides this, as it does for Flask's `url_for` and Django's
  `reverse`. The docs ("Serve below a sub-path") say a trusted proxy must
  set or remove that header, name `ProxyFix(x_prefix=1)` and
  `uvicorn --root-path`, warn about shared HTTP caches that ignore the
  header, and point to `security_script_integrity="citry"`, which makes the
  browser check each Citry script against a hash.

## Fixed during the review

- A `'` in the sub-path made every page fail, because the page and the
  check that looks for the Citry runtime on the page escaped it
  differently. It is now percent-encoded, and a test covers it.

## Not tested

- How gunicorn handles a `SCRIPT_NAME` request header.
- Django under a real server. Its sub-path reader was tested with crafted
  prefixes, without a browser.
- Translated pages (i18n) in a browser, WebSocket requests, and a real CDN.

## Follow-ups

- A `root_path` that does not start with a single `/` makes the page's
  URLs fall back to the site root while Starlette still routes requests
  with the raw value. Citry's own URLs then answer 404 and the page loses
  interactivity. This fails safe and is left as it is.
