## Who controls the input

This change decides how the browser runs the scripts of a page, in what
order, and what happens when one fails. Two kinds of page matter. A
**mounted page** is one that a web framework integration serves: Citry's
browser code adds each script as a `<script src>` element, one after
another. A **standalone page** is HTML that Citry writes without such an
integration, so the scripts sit inline in the page and the browser runs
them in tag order. The change adds three things:

- **A wrapper around each component's own `js`.** The server puts the
  script inside a `try` block that tells Citry's browser code ("the
  runtime") whether the script ran to its end, which the runtime keeps as
  a finish record. The script text comes from the component author. The
  wrapper text is Citry's own.
- **A new `finishKey` field on the script entries of the manifest.** The
  manifest is the JSON the server writes into the page, which the runtime
  reads to start the Vue app. The key is a 64-character hex digest that
  the server computes from the script text.
- **A rule that skips a script that fails to load.** On a mounted page, a
  script is skipped only when it is listed by URL, is from another origin
  than the page, does not register component options (Vue options set
  through `$component()`), and the browser reports its load as failed. The
  script URLs come from the app author (a `Dependencies` file, which is a
  file of scripts a component lists, or an extension), so they are
  author-only by design. What the browser reports about a failed load (a
  blocker, a policy, a failed integrity check, a network error) comes from
  the user's browser and network.

Markup that other people control can also reach the page: an injected
`<base>` element changes how the browser resolves relative URLs, and an
element such as `<img name="URL">` can replace a member of `document` with
the element. Page code can also call the runtime's functions. "Ruled out"
below covers what each of these can change, and what the wrapper does to
three things: the nonce (a one-time value that lets a script pass the
page's content security policy), the integrity hash (the digest the browser
checks a script against), and the opt-in output checks (`security_csp` and
`security_javascript`, which read the page's finished HTML).

The change also gives `onServerRender` callbacks (code a component
registers to run after it first mounts and after each server render) one
order: children before their parent, siblings in the order they first
mounted. Browser plugin scripts (scripts that add browser features, such
as the i18n runtime) run before component scripts on every page. A
callback that throws after startup stops the app, and a component that a
callback makes visible during a server render gets its own callback.
These decide when author-written code runs, not what code runs.

## How it was checked

The pull request lists the places from the security pass in `CLAUDE.md`
(Mechanism 7) that it touches, and says an independent reviewer checked
each one. What the record can show comes first from the shipped tests:

- **Tests that ship with the change.** The pull request does not describe
  the reviewer's code read in detail. The change adds 26 JavaScript tests
  in `script-order.test.mjs` (finish records, `finishKey` checks, the
  origin rule including a `<base>` element, a protocol-relative URL and a
  page whose origin is `null`, callback order, and the failure rule), and
  Python tests for where `finishKey` appears, which scripts are wrapped,
  and where plugin scripts go on both kinds of page. The browser tests
  cover plugin order, scripts that throw or fail to parse, a throwing
  `Dependencies` file, failed loads from another origin and from the page's
  own origin, a skipped script that a later fragment (HTML inserted after
  the page loads) tries again, a skipped file requested only once, and
  callback order and failure. The pull request says they pass on Chromium,
  Firefox and WebKit.
- **Content security policy (CSP).** According to the pull request, the
  reviewer ran Chromium under real CSP headers (the header that tells the
  browser which scripts may run) with a nonce only, a hash only, and
  `strict-dynamic` (which lets a trusted script load others), each with
  and without a throwing component script. The pull request adds that
  integrity and CSP hashes cover the final wrapped bytes, which matches
  `events.py`: it hashes the script text after wrapping it.
- **Other frameworks' advisories (Mechanism 8).** The reviewer checked the
  change against the kinds of bug listed in the maintainers' survey of
  published advisories for other frameworks. The pull request names
  eleven kinds, among them script loading, page members replaced by named
  elements, `__proto__` keys, writing data into server HTML, error pages,
  cache keys and slow regular expressions. It found none introduced.

## Ruled out

- **Breaking out of the script or the JSON.** The wrapper text holds no
  `</script`, `<!--` or `-->`. The key is a hex digest, so the string
  literal around it needs no escaping, and the manifest writes it through
  the existing JSON escaping.
- **A forged or misplaced `finishKey`.** The key must be 64 lowercase hex
  characters, and it is accepted only on a component entry whose source is
  one the server published itself. Python (`_validate_script_assets`) and
  the browser both enforce this, and `script-order.test.mjs` tests the
  browser side for a wrong format, an extension script and an external
  source. The three existing browser tests that copy a script entry and
  give it an external source drop the field from the copy, so they keep
  testing what they were written for.
- **Page code forging a finish record.** Only `finishScript` writes a
  record, and it rejects a key that is not a 64-character hex string.
  Page code can still call it, but the pull request judges that this only
  hides the failure of that component's own script.
- **Keys that reach inherited properties.** The runtime keeps finish
  records in a `Map` (a JavaScript lookup table with no inherited keys),
  so a key such as `__proto__` reaches only its own entry.
- **A `<base>` element or a replaced `document.URL`.** The skip rule
  resolves a script URL against the page's own address (`pageDocument.URL`),
  not against the base URL, so an injected `<base>` element cannot make the
  app's own file look third-party. `pageDocument` is the runtime's wrapper
  that reads built-in `document` members, so `<img name="URL">` does not
  replace the value. A script URL that does not parse, and a page or script
  whose origin is `null`, count as the app's own, so the script is not
  skipped and still stops startup. The `<base>` case is a JavaScript test.
  The change adds no test that places an `<img name="URL">` in a page, so
  that case rests on how the code reads the value.
- **Skipping more than a blocked third-party file.** The rule never skips
  a component script that Citry published, a script that registers
  options, or a script with a `finishKey`. Every other failed
  load stops startup.
- **The nonce and the opt-in output checks.** Reordered plugin scripts,
  wrapped inline component scripts on a standalone page, scripts the
  runtime adds on a mounted page, and fragments get the nonce the same way
  as before this change. The `security_csp` and `security_javascript`
  checks decide from script attributes, which the wrapper does not change.
  On a standalone page they also see the wrapped bytes. The three modes of
  those checks (warn, forbid, omit) give the same results as before this
  change, and an omitted script leaves no `finishKey`.
- **Error text in the page.** The new error and warning messages go only
  to the console and to the window's `error` event, never into page HTML.
- **A page that runs without a skipped file.** This is accepted on
  purpose. Citry cannot tell the app's own CDN from a third party, so a
  file from another origin is skipped whichever the author meant. The
  docs ("When a script fails" on the Component JS and CSS page) say to
  serve a file the page must not run without, such as a consent manager,
  from the page's own origin.

## Fixed during the review

- The code scanner flagged a regular expression in a test helper that
  looked for `<script>` tags and did not match upper-case tags. The pull
  request replaced it, and two helpers in `test_fragment_nonce_e2e.py`,
  with a small `html.parser.HTMLParser` reader. This changed test code
  only.
- The pull request says every finding of the technical review and of the
  re-review was fixed before merge, but it does not list them.

## Not tested

- Nothing in the change adds a new test that sets a CSP header. The
  Chromium runs under CSP headers (nonce only, hash only, `strict-dynamic`)
  are the reviewer's own, and the pull request does not say they ran in
  Firefox or WebKit.
- The narrow timing window around the moment Citry marks Vue startup
  finished. Issue
  [#664](https://github.com/citry-dev/citry/issues/664) says a
  script-finish report or a callback that arrives inside that window has
  no test.
- How the browser treats scripts on pages without the Vue runtime
  (`deps_strategy="simple"`). The change leaves that to the browser's own
  rules, and the design doc says only the written order is tested.
- A script that never finishes loading. There is no timeout.
- The pull request reports that locally the "runtime matches its source
  build" check failed because the installed Vue was 3.5.42 while the
  repository pins 3.5.44, and that a few other local failures (an old
  `citry_core` binary and the WebKit charset tests) occur without this
  change.
- A component script with `wrap=False`, or with a `type` that has
  parameters after the media type. Citry does not wrap these, so they get
  no `try` and no `finishKey`, and a throw in one does not stop the app
  (the pull request lists this under where the code differs from the
  design).
